# TASK-1218 — GTX 1080 model and slot comparison

Measured on 2026-09-23, on manu's GTX 1080. **The smaller model delivered about
2.87 times the throughput of 4B; increasing the smaller model from one to four
slots did not improve throughput or remove the long-request queue wait.** Keep
one slot for this workload. A production model change remains undecided.

## Throughput and latency

Each throughput result is the median of three shuffled passes over the same
44 texts, with four concurrent clients. The sample deliberately covers long
inputs; it is not a replay of the production arrival distribution.

| Configuration | Tokens/s, median (range) | VRAM peak, MiB | Short behind long, median |
| --- | --- | --- | --- |
| 4B Q8_0, one slot | 701 (701–702) | 6,655 | 12.580 s |
| 0.6B F16, one slot | 2,010 (2,008–2,010) | 3,983 | 4.389 s |
| 0.6B F16, four slots | 1,983 (1,978–1,989) | 6,671 | 4.418 s |

memory. These sequentially run arms establish no useful slot gain in this

Warm throughput is reported separately from this sequential pass. One-slot

The mixed tests submit the second request about 100 ms after the first, three
times in each order. Both one-slot arms used the original 301/7,601-token inputs.
The first short-first repeat returned in 41 ms (4B) / 26 ms (0.6B), before the
long request began, so that repeat does not establish overlap. Their other
short-first repeats did overlap, with short latency 336–338 / 145–153 ms.
The four-slot tests prepend unique per-repeat identifiers to prevent exact
repeat-cache hits: 308/7,608 tokens, seven more tokens per input. All six pairs
overlapped; short-first latency was 148–152 ms. The small input difference is
explicit: four-slot queue latency is not an exact-input paired estimate. It
still demonstrates a roughly 4.4-second short-behind-long wait on fresh inputs.

## Quality evidence and limits

- The CUDA 4B arm completed all 1,280 documents and 38 queries: **18/34 top-1
  (52.9%) and 25/34 top-5 (73.5%)**. Independent cosine replay reproduced every
  saved top-five ranking. Four negative queries were ranked; no abstention
  threshold was evaluated.
- The CUDA 0.6B quality pass stopped after **894/1,280** documents when timmy
  went offline. Its query pass never ran. There is **no completed matched CUDA
  retrieval-quality comparison** from this experiment.
- The earlier paired Mac fixture remains the completed model-quality evidence:
  4B **18/34 top-1, 24/34 top-5** versus 0.6B **16/34, 23/34**. That is a 5.9
  percentage-point top-1 reduction and a 2.9-point top-5 reduction. Do not mix
  the CUDA 4B score with the Mac 0.6B score. CUDA 4B's extra top-five hit was H3,
  where `bug-1015` crossed the fifth-place cutoff.
- All 44 sequential 0.6B sample vectors match exactly between one and four
  slots, with matching input hashes and cosine 1.0. This is a sequential
  vector check, not retrieval-quality validation under concurrent load.
- These are unprefixed whole-entry fixture results. Fresh-collection OV
  chunked retrieval, loaded recall p50/p95/p99, the 500 ms recall gate, and
  dimension-change/reindex cost remain unmeasured.

## Configuration and reproducibility

All arms used the production-pinned llama.cpp image, fully offloaded models,
four CPU threads, F16 KV, batch/ubatch 2,048, flash attention, and `--cache-ram 0`.
Each slot retained 8,192 context tokens: total context was 8,192 or 32,768.
Runtime `/props` verified the slot count and per-slot context. The isolated
Pod had no Service and never joined production routing; OV collections were
not modified. Request payloads specified `cache_prompt: false`, but host-cache
configuration alone is not proof of no repeat/prefix reuse; raw server metrics
and the fresh-input queue test are retained.
Throughput counter deltas showed only 0–1 cached tokens per one-slot pass and
zero for every four-slot pass, against about 125,178 processed tokens per pass.
The observed throughput comparison is therefore not driven by cache reuse.

## Interruption and restoration

The first planned embedding outage began at **18:22:48 UTC**. Timmy disappeared
from both Tailscale and the LAN around **20:15:28 UTC**, interrupting the 0.6B
quality pass and preventing API-based cleanup/restoration. The user reported
that their cat pressed timmy's power button and rebooted it. Manu stayed up;
its last inference samples were 70.25°C CPU and 66°C GPU, and the GPU became
idle. This interruption was not a benchmark thermal-guard stop.

After timmy returned, the scoped recovery removed the probe and restored the
saved deployment. Health plus a finite 2,560-dimensional embedding passed at
**20:23:41 UTC**; both OV deployments became Ready and `kubectl diff` against
the main embedder manifest was empty. The first interval was 120m53s.

The full matrix would also have exceeded the initial runtime estimate. A
longer window was requested but not approved. The bounded four-slot run began
at **20:25:19 UTC**, preserving the original 140-minute end budget. It ran only
the 44-text sequential pass, three four-client throughput passes, and fresh
queue probes; it omitted the two-slot arm and further full quality passes.
Final restoration passed at **20:33:28 UTC**, including HTTP health and a finite
2,560-dimensional embedding. The second interval was 8m09s, ending before the
original 20:42:48 deadline. Both OV deployments were Ready, the isolated Pod
was absent, and the production manifest diff was empty. The second run's
`restored.json` preserves the verification.

Outage-era capture and embedding recovery must be audited separately in
IDEA-1100. Ready pods and a successful new embedding do not prove missed pilot
turns were recovered. No production model or slot-count change was retained.
