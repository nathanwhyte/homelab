# Behavioral preferences

## Tool usage

- **Never use Bash for file content operations** — no `cat`/`head`/`tail`/`sed`/`awk` reads, no `>`/`>>`/heredoc writes, no `sed -i` edits. Use `Read` (or `ctx_execute_file` when analyzing rather than editing), `Write`, `Edit`, `Grep`, `Glob`. Bash is for git, mkdir, rm, mv, curl, and navigation only. No exceptions for "quick checks", whitespace/encoding inspection, or small snippets. `rg`/`fd` from Bash are acceptable only when the dedicated search tools don't fit. Full rationale and edge cases: [TOOL_USAGE.md](TOOL_USAGE.md).
- **Never use the built-in `WebFetch` tool** — it dumps raw page bytes into context. Fetch with `ctx_fetch_and_index(url, source)`, query with `ctx_search(queries: [...])`, extract/parse with `ctx_execute` using `fetch()` in the sandbox. Start with context-mode; do not try `WebFetch` first and fall back.
- **Agents and subagents must use context-mode** — ctx\_\* tools are deferred; load schemas before the first call with `ToolSearch("select:mcp__plugin_context-mode_context-mode__ctx_batch_execute,mcp__plugin_context-mode_context-mode__ctx_search,mcp__plugin_context-mode_context-mode__ctx_execute,mcp__plugin_context-mode_context-mode__ctx_execute_file,mcp__plugin_context-mode_context-mode__ctx_fetch_and_index")`. Prefer `ctx_batch_execute` over Bash for multi-command research, `ctx_execute_file` over Read for file analysis, and `ctx_fetch_and_index` over WebFetch for web content. The `<context_window_protection>` routing block is injected into agent prompts automatically — follow its tool hierarchy.

## Output

- Don't use words like "genuinely" or "honest". For example, if something is "genuinely confusing", just say it's confusing.
- **Use tables** for structured data, comparisons, or any output with 2+ columns of information; prefer them over bullet lists in those cases.
- **End-of-task summary**: finish with a short summary (2-4 sentences) of what was done, prefixed with a randomly-chosen emoji from the stamp pool: 🪿 🐘 🐦‍⬛ 🐋 🦉 🐢 🐙 🦎 🦦 🪴 🌵 🌿 🌱. Always use a space between the emoji and the text. The emoji has no fixed meaning — pick one at random each time for visual variety. Example: `🐋 Added the config file and committed as abc1234.`
- **Section headings use emoji prefixes**: one emoji at the start of the response — a colored-circle type marker optionally combined with a domain emoji. Always use a space between the emoji and the following text. Example: `🔴 ☁️ Cloud deploy failed` (error + cloud), `🟢 📊 Data pipeline succeeded` (success + data). Section headings after the first are plain text (no emoji). Status indicators (✅ ❌ ⚠️ ℹ️ ⏳ ✨ 🔄 🗑️) go inline at line start within sections, also with a space after the emoji.
- **File paths in output**: for compendium vault files and dotfiles config files, always show the full `~/`-prefixed path so it's copy-pasteable and unambiguous. Example: `~/code/compendium/bugs/mage/BUG-072-mapping-type-null-safety.md`, not just `BUG-072-mapping-type-null-safety.md`. For other project files, the filename alone is fine.
- **No box-drawing diagrams**: never use Unicode box-drawing characters (┌ ─ ┐ │ └ ┘) — the alignment is brittle. Use nested bullets, indented code blocks, tables, or Mermaid instead. (This bans hand-typed box drawing in chat replies; machine-generated `rich-fmt`/`rich` output displayed in a Bash tool panel is fine — see next rule.)
- **Colored terminal output via `rich-fmt` / forced color** (full playbook: `~/code/compendium/guides/tooling/GUIDE-023-other-using-rich-and-rich-cli-for-terminal-data-displays-and-repor.md`): Claude Code's Bash tool-output panel renders ANSI color, but captured stdout is a pipe (non-tty), so tools suppress color by default — force emission when the user should see styled output in the panel. `rich-fmt table|panel|tree --data '<json>'` (in `~/.local/bin/`) does this by default at a fixed 100-col width, and supports caller-judged emphasis (cell/header style dicts, `--box`) — use `--file`/stdin instead of inline `--data` for non-trivial payloads; for rich-based Python scripts, run them with `FORCE_COLOR=1`. Scope (per GUIDE-023 Step 8): use this only when (a) relaying a script's own styled/colorized output, (b) the shape is a tree or bordered panel with no markdown equivalent, or (c) showing a live styled render alongside the reply. A plain data table you are composing yourself stays a native markdown table in the reply — never rich-fmt. Use `--no-color` when redirecting to a file or pasting output into a markdown code fence (fences show raw escape codes as garbage).
- **Formatters are mandatory**: after every `Write` or `Edit`, run the file type's formatter (`uv run ruff format`, `npx prettier --write`, `gofmt -w`, `rustfmt`, `shfmt -w`, `sqlfluff fix`). Never fix indentation or spacing manually — if no formatter exists for the file type, leave it rather than hand-tweaking. Full table and rationale: [FORMATTING.md](FORMATTING.md).

## Subagent fan-out — parallelize independent flows

On capable (hosted Claude) sessions, actively fan out to parallel subagents when a flow is parallelizable, instead of grinding serially or dispatching one subagent and idling. This is the encourage-side counterpart to the local-model avoidance rule (IMPR-1066, `local-model-append.md`) — **on a local-model session that rule wins and overrides this section**; there, keep at most one subagent in flight.

### ⚠ Hard cap: one local-model consumer at a time

**This cap keys on what the work _drives_, not on what the session runs.** A hosted session (Opus/Sonnet) fanning out lanes that each call a local model is still N concurrent consumers of one GPU — the session's own model is irrelevant. This is the gap that crashed pop on 2026-07-27 (TASK-1169: several `lane-runner-local.py` subagents against `localhost:11434`, each holding its own KV cache, until RAM gave out).

**At most ONE local-model consumer may be in flight at any moment, across the whole session** — counting main-loop work _and_ subagents together. Never batch-spawn local-model lanes in one message; never start a second while one is running.

A task counts as a local-model consumer if it issues inference to a locally-served model. Recognize it by any of:

| Signal          | Examples                                                                      |
| --------------- | ----------------------------------------------------------------------------- |
| Host / endpoint | `localhost:11434`, `127.0.0.1:11434`, `_homelab_ollama_host`, timmy, `:8770`  |
| Tooling         | `ollama run/serve`, `lane-runner-local.py`, `ollama-thinking-proxy`, `mlx_lm` |
| Model names     | `qwen*`, `gemma*`, `zeta*`, any Modelfile tag in `dotfiles/ollama/`           |
| Skills          | `deep-dive-summary-sweep` and any GUIDE-1074 lane run in local mode           |

When several local-model items must be processed, **iterate them sequentially in one lane** — that is what the runners already do internally (`lane-runner-local.py` is "strictly sequential — one Ollama host, no concurrency" by design). Parallelism buys nothing there: requests serialize on the runner anyway, and the only thing that scales is RAM pressure. Fan out around the local call (gather inputs, apply results) but never fan out the call itself.

This cap is not overridden by "be comprehensive", `ultracode`, `Workflow`, or a user asking for speed — if throughput is the goal, say that the local runner is the bottleneck rather than adding lanes.

**Flow patterns worth fanning out** (the shapes the `bg-*` agents, `Workflow` patterns, and GUIDE-021 A7 bulk-edit pattern already target):

| Pattern                    | Example                                                                          |
| -------------------------- | -------------------------------------------------------------------------------- |
| Multi-file research/search | Independent sweeps across subsystems, directories, or naming conventions         |
| Per-item vault edits       | Bulk frontmatter sync, multi-item intake — one lane per item (GUIDE-021 A7)      |
| Review across dimensions   | Correctness / perf / security lanes over the same immutable diff                 |
| Multi-source investigation | Each agent probes a different source (code, logs, docs, tickets) blind to others |

**Fan-out-vs-serial heuristic:**

- **Fan out (≥2 subagents)** when subtasks are **independent** — no shared mutable state, no ordering dependency — **and** each is substantial enough to amortize spawn cost.
- **Stay inline (serial, main loop)** for trivial, tightly coupled, or dependent work, where parallel lanes would mostly duplicate each other or need to be serialized anyway.
- **Never dispatch one subagent and idle waiting on it** — that's a ~50% throughput loss for work that either needed no subagent (do it inline) or wanted several (fan out ≥2). One-and-idle is the anti-pattern this rule exists to kill.
- Keep fan-out lanes read-only unless the task is an isolated per-item write (worktree isolation for parallel mutation); dedupe and verify candidate results in the parent before acting on them.
- **Before fanning out, check whether the lanes call a local model.** If they do, the hard cap above applies and the answer is one sequential lane — no exceptions.

## PR review parallelization

The PR-review case is a specific instance of the fan-out heuristic above. After gathering PR metadata, repository instructions, changed files, and exact base/head SHAs, use parallel subagents whenever the review has independent subsystems or concerns and agent capacity is available.

- Partition heterogeneous PRs by subsystem. Otherwise, use separate lanes for correctness/runtime contracts, tests/edge cases, and security/performance/operational impact.
- Give each lane the same immutable PR context and a non-overlapping scope. Keep subagents read-only: they must not edit files, post comments, or submit reviews.
- Require candidate findings to include severity, `file:line`, concrete evidence, and validation performed. While lanes run, use the parent agent for local checks and cross-cutting analysis.
- Deduplicate and independently verify every candidate against the latest PR head. Drop speculative or stale findings; only the parent agent posts the consolidated review and verdict.
- Keep small or tightly coupled PRs single-agent when parallel lanes would mostly duplicate work.

## Deep research — start narrow

A full-scope `deep-research` run (6+ dimensions) can consume 3M+ subagent tokens. Stage the scope: targeted lookup (1-2 angles) → focused compare (2-3 options) → dimension deep-dive → full landscape scan (first-time broad surveys only — say so and get confirmation first). Frame `args` around a concrete decision or comparison, never an open-ended question, and never re-run a full scan on a topic already surveyed.

## Bare repositories with linked worktrees

`/Users/noot/code/dipdash` and `/Users/noot/code/mage` are **bare** Git repositories that manage sibling worktrees. They are not normal working trees — the repo root holds only git internals (`HEAD`, `config`, `objects/`, `refs/`), and every checkout is a sibling directory beside it, named after the branch/ticket:

```text
~/code/dipdash/                      bare root — no source files here
├── main/                            the `main` branch  ← default working location
└── OWL-NNNNN-<ticket-slug>/         one directory per additional branch
```

- Run `git worktree list` before starting work and use the worktree that owns the target branch.
- The `main` branch lives in each repository's `main/` worktree. Never switch that worktree to a feature branch.
- **Paths are one level deeper than they look**: `~/code/dipdash/main/…`, `~/code/mage/main/…`. A bare `~/code/dipdash/<src-dir>` path is stale.
- Run status, tests, formatting, commits, rebases, and project-file edits from the appropriate worktree, not the bare root.
- Preserve uncommitted changes in every worktree and do not modify unrelated worktrees.
- Create/remove with `git -C <repo> worktree add <slug> -b <branch> origin/main` / `worktree remove <slug>`. If a bare repo's directory is ever moved, worktrees break with `prunable` — repair via `git worktree repair <new-path>…` (never `prune`, which deletes the entries).

## Switching the session into a worktree (EnterWorktree / ExitWorktree)

Claude Code exposes an `EnterWorktree` tool that moves the **session's** working directory into a worktree persistently — unlike `cd` in the Bash tool, whose effect is reset to the session's launch directory on every call. Use it only when explicitly asked to work in a worktree (that is the tool's own gate).

- **Enter an existing worktree**: `EnterWorktree(path: "<abs path>")`. The path must already appear in `git worktree list` for the repo. This is the right mode for these bare repos: create the worktree first with `git worktree add <sibling-path> <branch>` (or `-b <branch>`), then `EnterWorktree` into it. A `path`-entered worktree is left on disk on exit — never deleted.
- **Create a fresh worktree**: `EnterWorktree(name: "<name>")` makes a new worktree under `.claude/worktrees/` on a new branch off `origin/<default>`. Avoid this for the bare repos above — their worktrees live as siblings of the bare root, not under `.claude/worktrees/`; use the `git worktree add` + `path` flow instead so the layout stays consistent.
- **Leave**: `ExitWorktree(action: "keep")` returns the session to the launch directory, leaving the worktree intact (the correct choice for `path`-entered worktrees). `action: "remove"` only deletes worktrees this session created via `EnterWorktree(name:)`, and refuses to drop uncommitted work unless `discard_changes: true`.
- Never switch a `main/` worktree onto a feature branch to satisfy an enter — add the feature worktree as a sibling and enter that instead. (Doing the former once put the branch on `dipdash/main` and needed manual cleanup.)

## Git Commit Guidance

**Every workflow that writes files must end with a git commit.** This is not optional. If you create, update, move, or delete vault files, you must commit those changes before reporting the workflow as complete. The only exception is read-only operations (query, lint).

### Machine-branch topology (PROJ-1017, live since 2026-07-22)

Each machine commits day-to-day work to its own long-running **machine branch** — `pop` on the personal MacBook, `workbook` on the work MacBook. The shared checkout sits on the machine branch; **sessions never need to reference `main` for routine work** — commit and push whatever branch the shared checkout has checked out. `main` is a curated integration target that only advances via GitHub PRs:

- **Compaction PRs** (the normal path): the machine branch → `main`, merged with a **merge commit** (never squash — squash breaks the ff-only sync and is reserved for ordinary worktree PRs). Trigger is manual at stint boundaries, with an advisory nudge when the branch is ~30 commits or ~7 days ahead of `main`. After the merge, sync the machine branch with `git fetch origin && git merge --ff-only origin/main`. Only the **merged** branch syncs; the other machine's branch keeps diverging until its own compaction PR.
- **Cluster cron PRs**: the hermes cluster jobs operate on `main` PR-mediated as before — the cluster is a third machine whose stable base is `main`.

Guard rails (best-effort, hook-installed clones only — run `_scripts/install-hooks.sh` once per machine): a pre-commit hook blocks commits made while `main` is checked out (`COMPENDIUM_ALLOW_MAIN=1` overrides for sanctioned main work), and a **raw** git pre-push hook (symlinked into the shared `.git/hooks` by the installer — deliberately not a pre-commit-framework hook, which sees only the first pushed ref) blocks any push that updates or deletes `refs/heads/main`, across every refspec of a multi-ref push and from every linked worktree and checked-out branch. The same push hook also protects the **machine branches** (IMPR-1099): it blocks pushing to the branch this machine does not own, and blocks rewriting (non-fast-forward) or deleting its own — `COMPENDIUM_ALLOW_BRANCH_FORCE=1` overrides for sanctioned repairs, and machine ownership can be declared explicitly with `git config compendium.machineBranch <branch>`. Feature/worktree branches are untouched, force-pushes included. Transitional note: a checkout of `main` uses `main`'s own `.pre-commit-config.yaml`, so the **commit** guard binds on `main` only after the first compaction PR lands the config there; the **push** guard lives in `.git/hooks` and binds regardless of the checked-out branch.

Drift from `main` is **expected state, not a problem**: content merged to `main` by the other machine or cluster jobs arrives at this machine at its next compaction sync. Cross-machine visibility between compactions comes from fetched refs (`git fetch origin <other-branch>` + `git grep` — see the intake dup-check rules and TASK-1153).

### Commit, push, and fetch — commit first, end in a PR or check-in

**Commit first, always.** Never run `git rebase` or `git pull --rebase` with uncommitted changes — rebase refuses on a dirty tree, and stashing around it invites the shared-stash hazards described in the worktree rules. The order is: stage → pre-commit → commit → push.

**On the machine branch and on feature/worktree branches, do NOT routinely rebase onto `origin/main`.** Worktree branches are long-lived; rebasing onto main mid-session replays the entire branch history (repeated conflict resolution for commits that were already resolved once) and rewrites published history, forcing a force-push. Worktree branches base on and merge back into the **machine branch** (the repo's `worktree.baseRef: head` setting handles the base automatically). Instead:

- **After each commit, push immediately**: `git push origin <branch>` (for shared-checkout work that's the machine branch — pushing also protects freshly-allocated IDs via the allocator's remote scan). Don't wait for a batch or an approval gate.
- **If the push is rejected** because the remote branch moved (another session pushed to the same branch), sync with the branch's own remote — not main: `git pull --rebase origin <branch>`, then push again.
- **Fetch occasionally for awareness** (`git fetch origin` is cheap), but drift from `main` is information, not a problem to fix on every commit — under the machine-branch topology it resolves at the next compaction PR, not per-commit.
- **End the session with a PR or a check-in — never an automatic rebase.** At integration time, push the branch and open the PR **as it stands**, then let GitHub report mergeability. Drift from `main` is information to surface in your summary, not something to silently resolve. Rebase only when (a) the user asks, or (b) GitHub reports the PR is not mergeable — and in case (b), check in first rather than resolving unattended. Rationale: an unattended rebase resolves other sessions' `index.md` conflicts with no one watching, and a wrong union silently drops another session's entry. A conflicted PR is a visible, recoverable state; a bad auto-resolution is neither.
- **If a rebase is sanctioned and the branch was already pushed**, follow it with `git push --force-with-lease` (never bare `--force`), and say so in your summary. When resolving `index.md`, verify the union — every side's entries present — and report the count.

**Commits on `main` are exceptional** (machine-branch topology): the pre-commit guard blocks them by design. When the user explicitly sanctions main work (`COMPENDIUM_ALLOW_MAIN=1`), the old rules apply: commit first, then `git fetch origin` and, if `origin/main` has advanced, `git rebase origin/main` (tree is clean now, so this is safe). Never push `main` directly — the pre-push guard blocks it; `main` advances via PRs. If a truly exceptional direct push is user-sanctioned, `--no-verify` with the sanction recorded in your summary.

### When to commit

- Completing an item (moves to resolved/completed dir)
- A batch of related frontmatter updates across multiple items (e.g., sync `date_updated` for a sprint)
- Intake of a new item with its source material
- Completing a project with all its sub-items
- A logical group of changes that are closely related

### How to group commits

| What's changed                         | Suggested commit scope                                            |
| -------------------------------------- | ----------------------------------------------------------------- |
| Template frontmatter schema changes    | Single commit for all `_templates/` + `.claude/instructions/*.md` |
| Batch `date_updated` sync (sprint/OWL) | One commit per type (bugs, features, tasks)                       |
| Intake — new item + source material    | One commit per item + its `_sources/` files                       |
| Moving completed items to resolved/    | One commit for all items in that batch                            |
| Cross-link updates, wikilink fixes     | One commit for the batch                                          |
| Mixed changes across types             | One commit per type                                               |

### Commit message format

`<type>: <short description>`

**Good commit messages:**

- `bugs: add date_updated to 14 active bugs (OWL-19455 batch)`
- `FEAT-016: add adhoc template research sources`
- `templates: add release_date, clickup_id/clickup_url frontmatter fields`
- `bugs/resolved: move completed bugs to resolved directory`

### Pre-commit hooks

Always run `pre-commit run --files $(git diff --name-only --cached)` before committing to ensure markdown and YAML files pass formatting and linting checks.

### Avoid

- Committing unrelated changes together (e.g., a new feature intake + a batch of unrelated bug updates)
- Over-granular commits (one file per commit when they're clearly related)
- Rebasing a feature/worktree branch onto `origin/main` — on every commit, _or_ reflexively at PR time. Open the PR as it stands and let GitHub judge mergeability; rebase only when asked or when the PR is actually blocked
- Resolving another session's `index.md` conflict unattended — a wrong union silently drops their entry. Check in instead
- Running `git rebase` with uncommitted changes — commit first, always

## Frontmatter YAML Gotchas

Four ways a frontmatter value silently breaks. `_scripts/lint-frontmatter.py` is the source of truth for which checks block commits (its module docstring lists them — unquoted-`#`, colon-space, body-leak, plus schema/status/completion-field/allow-list checks; leading-digit is the one below it does not yet catch) — this prose is belt to that lint's suspenders. Rule of thumb: **single-quote any string value containing `#`, `": "` (colon-space), or a leading digit.**

**1. Unquoted `#` → silent truncation.** An unquoted `" #"` (space-hash) starts a YAML comment, so `completed_in: compendium #69 + dotfiles #37` parses to just `"compendium"` — no error, wrong value. Single-quote it: `completed_in: "compendium #69 + dotfiles #37"`. `_scripts/complete-item.py` now auto-quotes refs, so prefer it for completions.

**2. Colon-space (`": "`) → parse break.** `retrieval_summary: Foo: bar` raises "mapping values are not allowed here" and breaks the whole block. Single-quote the value.

**3. Leading digit → numbered-list misparse.** If a string value begins with a digit (e.g., `8 of 10 questions`), YAML reads it as a numbered list and Obsidian frontmatter rendering breaks. Single-quote it, or for a multi-line field use a `>-` folded block scalar (never for `retrieval_summary`):

````yaml
status_detail: >-
8 of 10 design questions decided. 2 remain open for Joel:
  triggering mechanism (deploy-gate vs on-demand),
  pipeline automation (full fleet vs smoke suite).
```text

The `>-` folded block scalar produces a single logical line while avoiding the numeric-list ambiguity. See `.claude/instructions/projects.md` for the full list of fields affected.

**4. Body-leak past a mangled `---`.** If the closing `---` gets mangled, the H1 title and intro get absorbed into the frontmatter as junk keys (hit on PROJ-026/TASK-101), and `lint-frontmatter.py`'s required-key checks still pass. The malformed-key check (**fatal**) now catches it — keep a clean `---` on its own line closing the block.

## Worktree & Branch Conventions

**For longer-running compendium updates and research sessions, use Claude Code worktrees.** A worktree gives the session its own isolated working tree backed by a real git branch — safe from interruptions, crash-resilient, and mergeable back into `main` when done. This is the default for any task that touches more than a few files or spans an extended period (multi-item intake batches, project completions, deep research docs, plan creation, skill development).

**Merge back to the machine branch**: Worktree branches base on and merge back into the **machine branch** (`pop`/`workbook`) when they're done — the repo's `worktree.baseRef: head` setting makes `EnterWorktree` branch from it automatically; their content reaches `main` at the next compaction PR (PROJ-1017). Use `EnterWorktree` with `action: "keep"` at the end of a session and let the user review; use `action: "remove"` once the changes are committed and merged, then finish the post-merge cleanup procedure below — merging without cleaning up is an unfinished session.

**When NOT to use a worktree**:
- Simple single-item edits (one bug fix, one status transition) — just commit directly on the machine branch (`pop`/`workbook`) in the shared checkout.
- Read-only operations (querying, linting, searching).
- When the user asks for a specific branch name instead.

For other repositories (dipdash, mage, dotfiles, etc.) that have their own worktree conventions, follow those repos' rules. The restriction above applies only to `~/code/compendium/`.

Branches follow an `OWL-NNN/kebab-slug` format, e.g. `OWL-19576/source-file-names-improvements`.

### Post-merge cleanup is mandatory

A merged branch or worktree left behind is not "done" — stale branches accumulate, confuse later sessions and cron runs, and defeat the one-branch-per-run rules below. Every session that merges a branch cleans up **in the same session**, before reporting the work complete:

1. **Verify the merge actually landed** before deleting anything. For local merges, confirm the merge commit is on **the branch that received the merge** — the machine branch (`pop`/`workbook`) for worktree branches; `main` only for compaction/cron PRs. For PR merges, confirm with `gh pr view <N> --json state,mergedAt`. **Squash-merge caveat**: a squash-merged branch's tip is *never* reachable from `main`, so reachability checks (including `git-guard safe-branch-delete`) refuse even though the content is fully merged — this is the known IMPR-1060 gap. There, the merge evidence is `gh pr list --state merged --head <branch>`, not reachability.
2. **Remove the worktree**: `ExitWorktree` with `action: "remove"` (or `git worktree remove <path>`), then `git worktree prune`.
3. **Delete the branch** — local via `git-guard safe-branch-delete <branch>`, remote via `git push origin --delete <branch>`. If `safe-branch-delete` refuses on a branch that step 1 proved squash-merged, deleting anyway is sanctioned **only with that `gh` evidence recorded in your session summary** — say explicitly which branch was deleted and what proved the merge.
4. **End-of-session sweep**: run `git worktree list` and `git branch --list`. Any leftover branch/worktree you created must be either cleaned up or explicitly reported as intentionally kept (e.g. `EnterWorktree action: "keep"` pending user review) — never left behind silently.

The only branches that may outlive a session are ones the user is still reviewing; name them in your summary so the next session knows they're live, not stale.

### Shipping a `compendium-*` skill change

Skill changes span two repos. The end-to-end flow — the repo split (vault instructions/scripts vs `dotfiles` skills) and the **dual-copy sweep** (every `compendium-*` skill lives twice: `dotfiles/claude/skills/` **and** `dotfiles/hermes/skills/claude/skills/` — edit both, confirm parity with `diff -q`) — is documented in [`GUIDE-022`](guides/tooling/GUIDE-022-compendium-shipping-skill-changes-end-to-end.md). **Shipping ends when both halves land on `main`**; the MacBooks go live from there via the `~/.claude/skills` symlink. Bringing the `timmy` homelab node current is an optional follow-up (GUIDE-022 Step 4), not a gate — a `timmy` that is behind is not an unfinished ship. Authoring invariants, incl. the dual-copy rule and advisory-first check rollout, are in [`GUIDE-021`](guides/tooling/GUIDE-021-compendium-authoring-standard.md) A5.

### Cron job branch isolation

Cron jobs that modify the compendium (vault health scan, link integrity, research sweep, dipdash/mage scans) must follow these rules to prevent branch conflicts. **These jobs run on the hermes cluster against its own clone, where `main` remains the correct base** — cluster jobs integrate PR-mediated into `main`, which is allowed (the machine-branch topology reserves *direct pushes and day-to-day commits* for machine branches; PRs into `main` are the sanctioned advance path). A cron job must **never run on a machine's shared checkout** — flipping that checkout's branch would silently retarget the machine's session commits.

1. **Always `git checkout main && git pull` before creating a branch** (in the cluster clone). Never branch from a stale main.
2. **Never use `git checkout -b` while another branch is checked out.** Return to main first, pull, then branch.
3. **One branch per cron run.** If a previous run's branch still exists (e.g. `vault-health-2026-06-29`), delete it before creating a new one: `git branch -D <old-branch>`.
4. **Schedules are staggered** so no two compendium-modifying jobs run simultaneously:
   - Vault health scan: Monday 9:00
   - Vault link integrity: Monday 10:00 (after health scan finishes)
   - Research sweep: Tuesday 11:00 (different day entirely)
   - DipDash/Mage health scan: Sunday 6:00
   - DipDash/Mage refactor sweep: Sunday 7:00
5. **Clean up after PR merge — in the same run, not "eventually".** Follow the full post-merge cleanup procedure above (verify merge → remove worktree → delete local **and** remote branch → `git checkout main && git pull`). A run that ends with its merged branch still present has not finished; rule 3's pre-run delete is a backstop for crashed runs, not the normal cleanup path.

### Concurrent interactive sessions

Multiple sessions/agents can run against the shared `~/code/compendium` working tree at once — all committing to this machine's branch (`pop`/`workbook`), which the shared checkout keeps checked out. Same-machine contention is unchanged by the machine-branch topology; what the topology removes is **cross-machine** contention (the other machine writes to its own branch, and the curated indexes reconcile at compaction time). Sessions contend on the shared `index.md` files (the hand-maintained `log.md` operations logs were dropped in IMPR-1092 — the operations log is git history now), and a commit in one session can sweep up another's **uncommitted** edits to those files. The procedure:

- **Stage specific files, never `git add -A`,** when another agent may be active — so you neither absorb a neighbor's in-flight edits nor get swept into theirs.
- **Commit first, reconcile second.** Get your own work committed before any sync operation; never "clean up" the tree to make a sync work — an unexpected dirty path is probably a concurrent session's in-flight work, not yours to discard.
- **Reconcile, don't force.** If a push is rejected, `git pull --rebase origin <machine-branch>` and re-push; a rebase usually **auto-unions** competing `index.md` edits cleanly — verify the union (both sessions' entries present) after resolving. Never resolve contention with `reset --hard`/`checkout --`/`stash drop` in the shared checkout — the PreToolUse hook blocks these; use the `git-guard` equivalents (next section).
- **Branch work happens in a worktree.** Needing a clean tree while the shared checkout is dirty is the signal to `git worktree add`, not to clean the shared tree.
- The durable fix for the remaining `index.md` contention is deterministic index generation — tracked in [[IMPR-1050-other-derived-index-log-generation]].

For bulk frontmatter edits across many items, use the subagent bulk-edit pattern in [[GUIDE-021-compendium-authoring-standard|GUIDE-021]] A7.

### Destructive git operations are guarded (IMPR-1056)

**History surgery happens in a worktree; the shared checkout only advances via commit/pull.** A PreToolUse hook blocks the destructive-command class (`reset --hard`, `clean -f`, `checkout -- <path>`, `restore <path>`, `stash pop|drop`, `branch -D`, bare `push --force`) whenever the command targets `~/code/compendium` — because a concurrent session may hold uncommitted work the command would destroy (the 2026-07-12 incident). When you legitimately need one of these, use the recoverable `git-guard` equivalent (`git-guard clean-tree` / `safe-reset` / `safe-branch-delete`, in `~/.local/bin/`) — its checks test output emptiness and commit reachability, never exit codes — or do the operation on a worktree branch and merge back.

## General rules for editing live configs

Several directories in this repo are symlinked to live runtime locations (`~/.config/<name>`, `~/.hermes/`, `~/.claude/`, etc.). An edit here is an edit to a running tool's config. Follow these rules:

1. **Know what's live.** Before editing any file under `hermes/`, `claude/`, or `obsidian/`, check whether it's symlinked to a runtime path. Run `ls -la ~/.hermes/config.yaml ~/.claude/settings.json ~/code/compendium/.obsidian/` to see what's live.

2. **Only perform mass reformatting with explicit permission.** Do not run `pre-commit run --all-files`, `yq -i -P`, `prettier --write`, or any bulk formatter on `hermes/config.yaml`, `claude/settings.json`, or `obsidian/*.yaml` unless the user explicitly asks for it. The 2026-06-29 config corruption started when a bulk format pass appended unrelated YAML into `hermes/config.yaml`.

3. **No bulk renames or restructures of symlinked directories.** `hermes/skills/`, `claude/skills/`, and `obsidian/` are all symlinked to live locations. Renaming or moving files there breaks running agents, cron jobs, and Obsidian plugins.

4. **Validate before committing.** For YAML configs: `uv run --with pyyaml python3 -c "import yaml; yaml.safe_load(open('path/to/file.yaml').read())"` (system `python3` has no PyYAML). For JSON configs: `python3 -c "import json; json.load(open('path/to/file.json'))"`. If validation fails, revert — do not commit broken configs.

5. **Prefer targeted edits over wholesale replacements.** When adding a setting, add only the new key. When changing a value, change only that line. Avoid reformatting surrounding content.

### opencode (`opencode/`)

The local-model coding harness. `opencode.jsonc`, `tui.json`, `AGENTS.md` and the `themes/`, `commands/`, `agents/` directories are symlinked into the real `~/.config/opencode/` (opencode writes plugin `node_modules/` there, so the directory is never replaced). `model` and `small_model` both pin `qwen3.6:coding-35b` as of

and local Claude Code on one tag. Bare Pi is deliberately cloud-default as of

no-pin/picker arrangement was
reversed because picking a different tag evicts the resident model and its

losing harness (IDEA-1085). `ocg()` still reaches `gemma4:coding-26b`

Parity with the Claude Code config is deliberate, and stops in three specific places:

| Claude Code                         | opencode                                    | Note                                                        |
| ----------------------------------- | ------------------------------------------- | ----------------------------------------------------------- |
| `theme: custom:aura`                | `theme: aura` → `opencode/themes/aura.json` | Hand port — the two theme schemas share no key names        |
| `commands/*.md`                     | `commands/*.md` (`commit`, `describe_pr`)   | Commands cost **zero prefill** until invoked, unlike skills |
| `agents/*.md` subagents             | `agents/review.md` as a **primary** agent   | `permission.task` stays denied; primaries are unaffected    |
| `preferredNotifChannel: ghostty`    | `tui.json` → `attention.enabled`            | Off by default upstream; a local turn runs for minutes      |
| `editorMode: vim`                   | —                                           | No counterpart: "vim" appears 0× in the tui schema          |
| On-demand docs (`TOOL_USAGE.md`, …) | —                                           | `instructions` is **always** injected; see below            |

Three more traps, on top of the six recorded below:

7. **`tui.json` is a second config file**, with its own schema — `theme`, keybinds, `attention`, `diff_style`. Keys put in the wrong file load without complaint and do nothing. **`theme` is the one that bites**: with `"theme": "aura"` in `opencode.jsonc`, `opencode debug config` reports `theme: null`. It is plain JSON; only `opencode.jsonc` takes comments.
8. **Never add `instructions`.** It looks like the analog of the on-demand reference-doc table in `claude/CLAUDE.md`, but every listed file is injected into every prefill — the exact cost this config exists to avoid, with no lazy-load alternative while `permission.skill` is denied.
9. **The three config files merge, they do not shadow.** opencode loads `config.json`, `opencode.json`, then `opencode.jsonc` and later wins on conflicts (each gets a `loading path=` line in `~/.local/share/opencode/log/opencode.log`). An earlier comment in `install.sh` claimed a stray `opencode.json` would win outright — wrong, but the split is still how the claude-mem `plugin` key went untracked. Keep every authored key in `opencode.jsonc`.

10. **`plugins/`, `commands/`, `agents/` and `themes/` are auto-discovered** — a file dropped in `~/.config/opencode/plugins/` is picked up with **no config key naming it**. `opencode debug config` lists `plugins/claude-mem.js` with no `plugin` key present at all. Deleting the file, not removing a key, is what unregisters a plugin.

The claude-mem plugin **works** (verified 2026-07-30). It previously failed every startup with `Plugin export is not a function`; the obvious suspect was the `@opencode-ai/plugin` 1.16.2 pin against a 1.18.x runtime, but that was wrong — reinstalling the plugin fixed it with the pin unchanged. It was a stale build artifact.

11. **`opencode run` blocks on stdin when stdin is an open pipe.** Any non-interactive caller that leaves stdin open — the Claude Code Bash tool, a cron job, CI — hangs forever with **zero output and no error**, even though the model finished. Measured 2026-07-30: identical prompts took 12s with `</dev/null` and never returned without it. The session is written to the DB either way, so `opencode debug config`-style forensics show a completed turn while the process sits there.

    **Always redirect stdin for scripted runs:** `opencode run "…" </dev/null`. Diagnose a suspected hang by checking whether it ever opened a socket to the model (`lsof -nP -iTCP:11434`) — if not, it never reached inference.

12. **A tool-level `deny` is not a capability deny while `bash` is reachable.** The `review` agent originally paired `edit: deny` with `bash: allow`. Told to delete a function, the model hit `Model tried to call unavailable tool 'edit'` and then ran `sed -i` to do it anyway — successfully, then reported it as done. Any read-only agent must pattern-scope `bash` (`"*": deny` plus an explicit allowlist), not merely deny the write tools. Re-verified after the fix: the bypass is refused and the model says so.

Verifying this config, in decreasing order of how much they prove:

| Command                                             | Proves                                                         |
| --------------------------------------------------- | -------------------------------------------------------------- |
| `opencode debug config` — **see the warning below** | Resolved config — the only way to catch a silently-dropped key |
| `opencode agent list`                               | Agents registered                                              |
| `opencode run "…" </dev/null`                       | Plugins actually load (see the false negatives below)          |

All are headless — none costs a model call.

⚠ **`opencode debug config` prints resolved secrets.** It expands `${VAR}` from the
environment, so `mcp.*.headers.Authorization` and any credential env var appear in
full in its output — and therefore in any captured agent transcript or CI log.
Never run it bare where output is recorded. Pipe it through a redactor:

```bash
opencode debug config | python3 -c 'import json,sys,re; print(re.sub(r"(Bearer |\"[A-Z_]*KEY\": \")[^\"]+", r"\1[REDACTED]", sys.stdin.read()))'
```

⚠ **Plugin-load checks give false negatives.** `opencode serve` and a direct
`bun -e 'await import(...)'` both succeed against a plugin that opencode rejects,
because the loader validates **every** module export, not just `default`. Use a
real `run`, and note a _healthy_ load emits no log line — an empty grep proves
nothing on its own.

Narrow by default, the same way `lclaude()` is for Claude Code — prefill is the scarce resource on a local 26B. Measured on opencode 1.18.9 by pointing the shipped config at a mock OpenAI-compatible server and capturing its outbound HTTP body (2026-07-29): **~17.8k → ~7.4k tokens, 58.3% smaller**.

| Trim                                    | Saves         | Where            |
| --------------------------------------- | ------------- | ---------------- |
| `permission: {skill: "deny"}`           | ~4.6k tok     | `opencode.jsonc` |
| `permission: {task: "deny"}`            | ~964 tok      | `opencode.jsonc` |
| `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT=1` | ~5.4k tok     | `zsh/.zshrc`     |
| All 10 MCP servers `enabled: false`     | schema + init | `opencode.jsonc` |

Six things here are easy to break and were established by measurement, not docs:

1. **Thinking suppression needs camelCase `options.reasoningEffort: "none"`** — opencode translates it to `reasoning_effort` in the body, the only field Ollama 0.32.5 honors on `/v1/chat/completions` (the surface opencode uses). Snake_case `reasoning_effort` in config is silently dropped.
2. **`"reasoning": true` is required, but only safe when paired with an explicit effort.** On its own it makes opencode inject `reasoning_effort: "low"` — thinking ON. Alongside `options.reasoningEffort` it's both safe and necessary: without it opencode _discards_ the response's reasoning field, so asking for thinking costs 3.5–5.5× the completion tokens and displays nothing.
3. **A `permission` deny removes the tool's schema from the request**, not just the ability to call it — that is why the denies above are a prefill lever. Same technique as `claude/settings-local-model.json`.
4. **`~/.config/opencode/AGENTS.md` does NOT displace `~/.claude/CLAUDE.md`** despite opencode's docs saying it takes precedence. Measured additive; only the env var drops it.
5. **The schema key names are singular.** The config page's schema index lists section headings (`permissions`, `mcp-servers`, `formatters`, `sharing`, `models`); the literal keys are `permission`, `mcp`, `formatter`, `share`, `model`. A config written from that index loads without complaint and does nothing.
6. **`formatter` omitted means all formatters off**, and `formatter: true` is conditional per built-in — each fails silently when its requirement is unmet. Prettier only activates when the project has prettier in `package.json`, so it does **not** fire in this repo; `opencode/AGENTS.md` still carries the formatter rule for markdown/JSON here.

`small_model` is deliberately the same model as `model`: with `OLLAMA_MAX_LOADED_MODELS=1`, a different small model evicts and reloads the resident 27 GB primary on every session-title generation.

**Permissions are fully permissive** — the equivalent of Claude Code's `--dangerously-skip-permissions`, matching how `lclaude()` runs. Two guards are therefore disarmed on purpose: `.env` reads (opencode's default denies them) and `external_directory` (which had caught the 26B retyping a path as `/Users/noat/...`). Both restore in one line; see the comments in `opencode.jsonc`. The only remaining denies are `skill`/`task`, which are prefill levers, not safety settings.

Shell surface in `zsh/.zshrc`: the two `OPENCODE_DISABLE_CLAUDE_CODE_*` env flags, plus `oc` (interactive; now opens on the pinned `qwen3.6:coding-35b` rather than the picker), `ocr` (one-shot via `ollama launch`), `ocg` (pinned to `gemma4:coding-26b`), and `occ`/`ocm`/`ocstat`. The model-switch, thinking-debug, and warmup aliases were trimmed 2026-08-01; thinking checks go through `opencode run --thinking 'say OK' </dev/null` (a `run`-only flag — the TUI has no equivalent, so there is no `ocr` form) and `--variant low|medium|high|max` to turn thinking on per invocation.

Full per-surface thinking matrix: `claude/GUARDRAILS.md` §1. Vault entries: INFO-1134 (thinking matrix), INFO-1135/INFO-1136 (opencode config + extensibility), GUIDE-1076 (setup procedure).

### Hermes (`hermes/`)

Config for the Hermes AI agent. Only authored config is tracked (config.yaml, SOUL.md, hooks, skins, skill definitions). Runtime state (state.db, sessions, logs, secrets) lives in the real `~/.hermes/` directory, never in git.

**⚠️ CRITICAL: `hermes/config.yaml` is a live runtime config.** It is symlinked to `~/.hermes/config.yaml` which Hermes reads on every turn. Non-Hermes agents (Claude Code, Codex, etc.) must follow these rules:

1. **Never run `hermes config set`, `hermes doctor --fix`, or any Hermes CLI command.** These mutate the live config and can break the running Hermes instance. Only Hermes itself should invoke these.

2. **Never append unrelated YAML documents to `hermes/config.yaml`.** The file must contain exactly one YAML document. A second `---` separator followed by unrelated content (pre-commit config, GitHub PR sections, etc.) makes the file unparseable by `yaml.safe_load()`, causing Hermes to fall back to defaults and lose all provider/auxiliary config. This is what caused the 2026-06-29 config corruption (commit `1147dfd`).

3. **Only make targeted, minimal edits to `hermes/config.yaml` when explicitly asked.** Do not reformat, reflow, or restructure the file. The Hermes config parser is sensitive to YAML formatting changes (personality strings, empty-value quoting, etc.).

4. **Validate YAML before and after any edit.** Run `uv run --with pyyaml python3 -c "import yaml; yaml.safe_load(open('hermes/config.yaml').read())"` (system `python3` has no PyYAML) to confirm the file parses as a single document. If it fails, revert your change immediately.

5. **`hermes/skills/` is also a live symlink target.** Do not mass-edit, rename, or restructure skill directories unless you are a Hermes agent or explicitly asked. Cron jobs depend on skill names resolving directly in `~/.hermes/skills/`.

## Ground rules (safety first)

- **Do not apply changes to a live cluster unless explicitly asked.** Avoid running `kubectl apply`, `helm install/upgrade`, or anything that mutates cluster state unless the user requests it.
- **Do not introduce or commit secrets.**
  - Prefer referencing existing `Secret` resources (by name) rather than inlining secret material.
  - If a manifest must reference a secret key/token/cert, add a placeholder and document what’s required.
  - The repo ignores common sensitive patterns (see `.gitignore`), but still treat all credentials as out-of-scope.
- **Don’t change global tooling config** (git config, shell config, etc.) unless asked.

## Worktree & Branch Conventions

**`~/code/homelab` is a BARE repository with sibling worktrees — it is not a normal working tree.** (Migrated 2026-07-19; the same layout `~/code/qpendium` uses.) There are no source files at the repo root — only git internals (`HEAD`, `config`, `objects/`, `refs/`, `worktrees/`). Every checkout lives in its own sibling directory:

```text
~/code/homelab/                          bare root — never edit or run builds here
├── main/                                the `main` branch  ← default working location
├── llama-timmy-edit-prediction/         llama/timmy-edit-prediction-node
└── impr-1068-embedder-vulkan/           worktree-impr-1068-embedder-vulkan
```

**Consequences for every session:**

- Run `git worktree list` before starting, and work in the worktree that owns your target branch.
- `main` lives at `~/code/homelab/main/`. **Never switch that worktree to a feature branch.**
- Paths that used to be `~/code/homelab/<dir>` are now `~/code/homelab/main/<dir>` — e.g. `~/code/homelab/main/compendium/cluster-sync.sh`, `kubectl apply -k ~/code/homelab/main/copyparty/`.
- Run status, tests, formatting, commits, and rebases from a worktree, never the bare root.
- Preserve uncommitted changes in every worktree; do not modify unrelated worktrees.

### Setup

Worktrees are sibling directories created from the bare root:

```bash
git -C ~/code/homelab worktree add <slug> -b <branch> origin/main
cd ~/code/homelab/<slug>
# Work here...
```

Remove one when finished (this deletes the directory, so commit or merge first):

```bash
git -C ~/code/homelab worktree remove <slug>
```

**Gotchas:**

- Worktree admin files store **absolute paths**. If the repo directory is ever moved or renamed, every worktree breaks with `prunable`. Fix with `git worktree repair <new-path>…` passing the new paths explicitly — **never** `git worktree prune`, which deletes the admin entries instead of repairing them.
- Local ignore patterns live in `~/code/homelab/info/exclude` (the bare-repo equivalent of `.git/info/exclude`). They are **not** tracked and are **not** copied by `git clone` — this file carries the `rotated-creds-*.txt` and `**/.claude/*` exclusions, so preserve it in any future repo move.
- Do not set `extensions.worktreeConfig`. With it enabled, the root's `core.bare = true` leaks into every linked worktree and breaks `git status` ("this operation must be run in a work tree").

### Branch naming

Follow the existing `type/description` convention used in this repo:

- `docs/drift-fix-<date>` — documentation corrections and drift fixes
- `feat/<short-description>` — new features or services
- `fix/<short-description>` — bug fixes
- `scan/<description>` — scan or audit outputs

All PRs target `main` directly.

### When to use a worktree

- Multi-file changes (manifest updates across services, config refactors)
- Long-running sessions that might be interrupted
- Parallel work on the same repo (one worktree per branch, never share)

### When NOT to use a worktree

- Simple single-file edits (one manifest tweak, one values override) — just commit on `main` directly.
- Read-only operations (querying, linting, searching, `kubectl get`).
- When the user asks for a specific branch name instead.

### Cleanup

After a PR merges or is closed:

```bash
cd ~/code/homelab
git worktree remove .worktrees/<slug>
git branch -d <branch>
```

Never leave orphaned worktrees — they lock branches and waste disk space. If a directory was deleted manually, run `git worktree prune` before adding new worktrees.

### Parallel work rules

- **One worktree per branch.** Never check out the same branch in two worktrees.
- **Rebase before push.** Always `git fetch origin main && git rebase origin/main` before pushing.
- **Clean up after merge.** Remove the worktree and delete the local branch when the PR is done.
- See the `git-parallel-work` skill for the full protocol (merge ordering, YAML conflict avoidance, post-merge cascade, cron PR supersession).

## Change hygiene

- Keep changes scoped to the service you're touching.
- Update `README.md` only when adding/removing services or materially changing how deployments work.
