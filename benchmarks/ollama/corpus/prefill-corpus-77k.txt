# Behavioral preferences

## Tool usage

- **Never use Bash for file content operations** — no `cat`/`head`/`tail`/`sed`/`awk` reads, no `>`/`>>`/heredoc writes, no `sed -i` edits. Use `Read` (or `ctx_execute_file` when analyzing rather than editing), `Write`, `Edit`, `Grep`, `Glob`. Bash is for git, mkdir, rm, mv, curl, and navigation only. No exceptions for "quick checks", whitespace/encoding inspection, or small snippets. `rg`/`fd` from Bash are acceptable only when the dedicated search tools don't fit. Full rationale and edge cases: [TOOL_USAGE.md](TOOL_USAGE.md).
- **Never use the built-in `WebFetch` tool** — it dumps raw page bytes into context. Fetch with `ctx_fetch_and_index(url, source)`, query with `ctx_search(queries: [...])`, extract/parse with `ctx_execute` using `fetch()` in the sandbox. Start with context-mode; do not try `WebFetch` first and fall back.
- **Agents and subagents must use context-mode** — ctx\_\* tools are deferred; load schemas before the first call with `ToolSearch("select:mcp__plugin_context-mode_context-mode__ctx_batch_execute,mcp__plugin_context-mode_context-mode__ctx_search,mcp__plugin_context-mode_context-mode__ctx_execute,mcp__plugin_context-mode_context-mode__ctx_execute_file,mcp__plugin_context-mode_context-mode__ctx_fetch_and_index")`. Prefer `ctx_batch_execute` over Bash for multi-command research, `ctx_execute_file` over Read for file analysis, and `ctx_fetch_and_index` over WebFetch for web content. The `<context_window_protection>` routing block is injected into agent prompts automatically — follow its tool hierarchy.

## Output

- Don't use words like "genuinely" or "honest". For example, if something is "genuinely confusing", just say it's confusing.
- **Use tables** for structured data, comparisons, or any output with 2+ columns of information; prefer them over bullet lists in those cases.
- **End-of-task summary**: finish with a short summary (2-4 sentences) of what was done, prefixed with a randomly-chosen emoji from the stamp pool: 🪿 🐘 🐦‍⬛ 🐋 🦉 🐢 🐙 🦎 🦦 🪴 🌵 🌿 🌱. Always use a space between the emoji and the text. The emoji has no fixed meaning — pick one at random each time for visual variety. Example: `🐋 Added the config file and committed as abc1234.`
- **Section headings use emoji prefixes**: one emoji at the start of the response — a colored-circle type marker optionally combined with a domain emoji. Always use a space between the emoji and the following text. Example: `🔴 ☁️ Cloud deploy failed` (error + cloud), `🟢 📊 Data pipeline succeeded` (success + data). Section headings after the first are plain text (no emoji). Status indicators (✅ ❌ ⚠️ ℹ️ ⏳ ✨ 🔄 🗑️) go inline at line start within sections, also with a space after the emoji.
- **File paths in output**: for compendium vault files and dotfiles config files, always show the full `~/`-prefixed path so it's copy-pasteable and unambiguous. Example: `~/code/compendium/bugs/mage/BUG-072-mapping-type-null-safety.md`, not just `BUG-072-mapping-type-null-safety.md`. For other project files, the filename alone is fine.
- **No box-drawing diagrams**: never use Unicode box-drawing characters (┌ ─ ┐ │ └ ┘) — the alignment is brittle. Use nested bullets, indented code blocks, tables, or Mermaid instead. (This bans hand-typed box drawing in chat replies; machine-generated `rich-fmt`/`rich` output displayed in a Bash tool panel is fine — see next rule.)
- **Colored terminal output via `rich-fmt` / forced color** (full playbook: `~/code/compendium/guides/tooling/GUIDE-023-other-using-rich-and-rich-cli-for-terminal-data-displays-and-repor.md`): Claude Code's Bash tool-output panel renders ANSI color, but captured stdout is a pipe (non-tty), so tools suppress color by default — force emission when the user should see styled output in the panel. `rich-fmt table|panel|tree --data '<json>'` (in `~/.local/bin/`) does this by default at a fixed 100-col width, and supports caller-judged emphasis (cell/header style dicts, `--box`) — use `--file`/stdin instead of inline `--data` for non-trivial payloads; for rich-based Python scripts, run them with `FORCE_COLOR=1`. Scope (per GUIDE-023 Step 8): use this only when (a) relaying a script's own styled/colorized output, (b) the shape is a tree or bordered panel with no markdown equivalent, or (c) showing a live styled render alongside the reply. A plain data table you are composing yourself stays a native markdown table in the reply — never rich-fmt. Use `--no-color` when redirecting to a file or pasting output into a markdown code fence (fences show raw escape codes as garbage).
- **Formatters are mandatory**: after every `Write` or `Edit`, run the file type's formatter (`uv run ruff format`, `npx prettier --write`, `gofmt -w`, `rustfmt`, `shfmt -w`, `sqlfluff fix`). Never fix indentation or spacing manually — if no formatter exists for the file type, leave it rather than hand-tweaking. Full table and rationale: [FORMATTING.md](FORMATTING.md).

## Subagent fan-out — parallelize independent flows

On capable (hosted Claude) sessions, actively fan out to parallel subagents when a flow is parallelizable, instead of grinding serially or dispatching one subagent and idling. This is the encourage-side counterpart to the local-model avoidance rule (IMPR-1066, `local-model-append.md`) — **on a local-model session that rule wins and overrides this section**; there, keep at most one subagent in flight.

### ⚠ Hard cap: one local-model consumer at a time

**This cap keys on what the work _drives_, not on what the session runs.** A hosted session (Opus/Sonnet) fanning out lanes that each call a local model is still N concurrent consumers of one GPU — the session's own model is irrelevant. This is the gap that crashed pop on 2026-07-27 (TASK-1169: several `lane-runner-local.py` subagents against `localhost:11434`, each holding its own KV cache, until RAM gave out).

**At most ONE local-model consumer may be in flight at any moment, across the whole session** — counting main-loop work _and_ subagents together. Never batch-spawn local-model lanes in one message; never start a second while one is running.

A task counts as a local-model consumer if it issues inference to a locally-served model. Recognize it by any of:

| Signal          | Examples                                                                      |
| --------------- | ----------------------------------------------------------------------------- |
| Host / endpoint | `localhost:11434`, `127.0.0.1:11434`, `_homelab_ollama_host`, timmy, `:8770`  |
| Tooling         | `ollama run/serve`, `lane-runner-local.py`, `ollama-thinking-proxy`, `mlx_lm` |
| Model names     | `qwen*`, `gemma*`, `zeta*`, any Modelfile tag in `dotfiles/ollama/`           |
| Skills          | `deep-dive-summary-sweep` and any GUIDE-1074 lane run in local mode           |

When several local-model items must be processed, **iterate them sequentially in one lane** — that is what the runners already do internally (`lane-runner-local.py` is "strictly sequential — one Ollama host, no concurrency" by design). Parallelism buys nothing there: requests serialize on the runner anyway, and the only thing that scales is RAM pressure. Fan out around the local call (gather inputs, apply results) but never fan out the call itself.

This cap is not overridden by "be comprehensive", `ultracode`, `Workflow`, or a user asking for speed — if throughput is the goal, say that the local runner is the bottleneck rather than adding lanes.

**Flow patterns worth fanning out** (the shapes the `bg-*` agents, `Workflow` patterns, and GUIDE-021 A7 bulk-edit pattern already target):

| Pattern                    | Example                                                                          |
| -------------------------- | -------------------------------------------------------------------------------- |
| Multi-file research/search | Independent sweeps across subsystems, directories, or naming conventions         |
| Per-item vault edits       | Bulk frontmatter sync, multi-item intake — one lane per item (GUIDE-021 A7)      |
| Review across dimensions   | Correctness / perf / security lanes over the same immutable diff                 |
| Multi-source investigation | Each agent probes a different source (code, logs, docs, tickets) blind to others |

**Fan-out-vs-serial heuristic:**

- **Fan out (≥2 subagents)** when subtasks are **independent** — no shared mutable state, no ordering dependency — **and** each is substantial enough to amortize spawn cost.
- **Stay inline (serial, main loop)** for trivial, tightly coupled, or dependent work, where parallel lanes would mostly duplicate each other or need to be serialized anyway.
- **Never dispatch one subagent and idle waiting on it** — that's a ~50% throughput loss for work that either needed no subagent (do it inline) or wanted several (fan out ≥2). One-and-idle is the anti-pattern this rule exists to kill.
- Keep fan-out lanes read-only unless the task is an isolated per-item write (worktree isolation for parallel mutation); dedupe and verify candidate results in the parent before acting on them.
- **Before fanning out, check whether the lanes call a local model.** If they do, the hard cap above applies and the answer is one sequential lane — no exceptions.

## PR review parallelization

The PR-review case is a specific instance of the fan-out heuristic above. After gathering PR metadata, repository instructions, changed files, and exact base/head SHAs, use parallel subagents whenever the review has independent subsystems or concerns and agent capacity is available.

- Partition heterogeneous PRs by subsystem. Otherwise, use separate lanes for correctness/runtime contracts, tests/edge cases, and security/performance/operational impact.
- Give each lane the same immutable PR context and a non-overlapping scope. Keep subagents read-only: they must not edit files, post comments, or submit reviews.
- Require candidate findings to include severity, `file:line`, concrete evidence, and validation performed. While lanes run, use the parent agent for local checks and cross-cutting analysis.
- Deduplicate and independently verify every candidate against the latest PR head. Drop speculative or stale findings; only the parent agent posts the consolidated review and verdict.
- Keep small or tightly coupled PRs single-agent when parallel lanes would mostly duplicate work.

## Deep research — start narrow

A full-scope `deep-research` run (6+ dimensions) can consume 3M+ subagent tokens. Stage the scope: targeted lookup (1-2 angles) → focused compare (2-3 options) → dimension deep-dive → full landscape scan (first-time broad surveys only — say so and get confirmation first). Frame `args` around a concrete decision or comparison, never an open-ended question, and never re-run a full scan on a topic already surveyed.

## Bare repositories with linked worktrees

`/Users/noot/code/dipdash` and `/Users/noot/code/mage` are **bare** Git repositories that manage sibling worktrees. They are not normal working trees — the repo root holds only git internals (`HEAD`, `config`, `objects/`, `refs/`), and every checkout is a sibling directory beside it, named after the branch/ticket:

```text
~/code/dipdash/                      bare root — no source files here
├── main/                            the `main` branch  ← default working location
└── OWL-NNNNN-<ticket-slug>/         one directory per additional branch
```

- Run `git worktree list` before starting work and use the worktree that owns the target branch.
- The `main` branch lives in each repository's `main/` worktree. Never switch that worktree to a feature branch.
- **Paths are one level deeper than they look**: `~/code/dipdash/main/…`, `~/code/mage/main/…`. A bare `~/code/dipdash/<src-dir>` path is stale.
- Run status, tests, formatting, commits, rebases, and project-file edits from the appropriate worktree, not the bare root.
- Preserve uncommitted changes in every worktree and do not modify unrelated worktrees.
- Create/remove with `git -C <repo> worktree add <slug> -b <branch> origin/main` / `worktree remove <slug>`. If a bare repo's directory is ever moved, worktrees break with `prunable` — repair via `git worktree repair <new-path>…` (never `prune`, which deletes the entries).

## Switching the session into a worktree (EnterWorktree / ExitWorktree)

Claude Code exposes an `EnterWorktree` tool that moves the **session's** working directory into a worktree persistently — unlike `cd` in the Bash tool, whose effect is reset to the session's launch directory on every call. Use it only when explicitly asked to work in a worktree (that is the tool's own gate).

- **Enter an existing worktree**: `EnterWorktree(path: "<abs path>")`. The path must already appear in `git worktree list` for the repo. This is the right mode for these bare repos: create the worktree first with `git worktree add <sibling-path> <branch>` (or `-b <branch>`), then `EnterWorktree` into it. A `path`-entered worktree is left on disk on exit — never deleted.
- **Create a fresh worktree**: `EnterWorktree(name: "<name>")` makes a new worktree under `.claude/worktrees/` on a new branch off `origin/<default>`. Avoid this for the bare repos above — their worktrees live as siblings of the bare root, not under `.claude/worktrees/`; use the `git worktree add` + `path` flow instead so the layout stays consistent.
- **Leave**: `ExitWorktree(action: "keep")` returns the session to the launch directory, leaving the worktree intact (the correct choice for `path`-entered worktrees). `action: "remove"` only deletes worktrees this session created via `EnterWorktree(name:)`, and refuses to drop uncommitted work unless `discard_changes: true`.
- Never switch a `main/` worktree onto a feature branch to satisfy an enter — add the feature worktree as a sibling and enter that instead. (Doing the former once put the branch on `dipdash/main` and needed manual cleanup.)

## Git Commit Guidance

**Every workflow that writes files must end with a git commit.** This is not optional. If you create, update, move, or delete vault files, you must commit those changes before reporting the workflow as complete. The only exception is read-only operations (query, lint).

### Machine-branch topology (PROJ-1017, live since 2026-07-22)

Each machine commits day-to-day work to its own long-running **machine branch** — `pop` on the personal MacBook, `workbook` on the work MacBook. The shared checkout sits on the machine branch; **sessions never need to reference `main` for routine work** — commit and push whatever branch the shared checkout has checked out. `main` is a curated integration target that only advances via GitHub PRs:

- **Compaction PRs** (the normal path): the machine branch → `main`, merged with a **merge commit** (never squash — squash breaks the ff-only sync and is reserved for ordinary worktree PRs). Trigger is manual at stint boundaries, with an advisory nudge when the branch is ~30 commits or ~7 days ahead of `main`. After the merge, sync the machine branch with `git fetch origin && git merge --ff-only origin/main`. Only the **merged** branch syncs; the other machine's branch keeps diverging until its own compaction PR.
- **Cluster cron PRs**: the hermes cluster jobs operate on `main` PR-mediated as before — the cluster is a third machine whose stable base is `main`.

Guard rails (best-effort, hook-installed clones only — run `_scripts/install-hooks.sh` once per machine): a pre-commit hook blocks commits made while `main` is checked out (`COMPENDIUM_ALLOW_MAIN=1` overrides for sanctioned main work), and a **raw** git pre-push hook (symlinked into the shared `.git/hooks` by the installer — deliberately not a pre-commit-framework hook, which sees only the first pushed ref) blocks any push that updates or deletes `refs/heads/main`, across every refspec of a multi-ref push and from every linked worktree and checked-out branch. The same push hook also protects the **machine branches** (IMPR-1099): it blocks pushing to the branch this machine does not own, and blocks rewriting (non-fast-forward) or deleting its own — `COMPENDIUM_ALLOW_BRANCH_FORCE=1` overrides for sanctioned repairs, and machine ownership can be declared explicitly with `git config compendium.machineBranch <branch>`. Feature/worktree branches are untouched, force-pushes included. Transitional note: a checkout of `main` uses `main`'s own `.pre-commit-config.yaml`, so the **commit** guard binds on `main` only after the first compaction PR lands the config there; the **push** guard lives in `.git/hooks` and binds regardless of the checked-out branch.

Drift from `main` is **expected state, not a problem**: content merged to `main` by the other machine or cluster jobs arrives at this machine at its next compaction sync. Cross-machine visibility between compactions comes from fetched refs (`git fetch origin <other-branch>` + `git grep` — see the intake dup-check rules and TASK-1153).

### Commit, push, and fetch — commit first, end in a PR or check-in

**Commit first, always.** Never run `git rebase` or `git pull --rebase` with uncommitted changes — rebase refuses on a dirty tree, and stashing around it invites the shared-stash hazards described in the worktree rules. The order is: stage → pre-commit → commit → push.

**On the machine branch and on feature/worktree branches, do NOT routinely rebase onto `origin/main`.** Worktree branches are long-lived; rebasing onto main mid-session replays the entire branch history (repeated conflict resolution for commits that were already resolved once) and rewrites published history, forcing a force-push. Worktree branches base on and merge back into the **machine branch** (the repo's `worktree.baseRef: head` setting handles the base automatically). Instead:

- **After each commit, push immediately**: `git push origin <branch>` (for shared-checkout work that's the machine branch — pushing also protects freshly-allocated IDs via the allocator's remote scan). Don't wait for a batch or an approval gate.
- **If the push is rejected** because the remote branch moved (another session pushed to the same branch), sync with the branch's own remote — not main: `git pull --rebase origin <branch>`, then push again.
- **Fetch occasionally for awareness** (`git fetch origin` is cheap), but drift from `main` is information, not a problem to fix on every commit — under the machine-branch topology it resolves at the next compaction PR, not per-commit.
- **End the session with a PR or a check-in — never an automatic rebase.** At integration time, push the branch and open the PR **as it stands**, then let GitHub report mergeability. Drift from `main` is information to surface in your summary, not something to silently resolve. Rebase only when (a) the user asks, or (b) GitHub reports the PR is not mergeable — and in case (b), check in first rather than resolving unattended. Rationale: an unattended rebase resolves other sessions' `index.md` conflicts with no one watching, and a wrong union silently drops another session's entry. A conflicted PR is a visible, recoverable state; a bad auto-resolution is neither.
- **If a rebase is sanctioned and the branch was already pushed**, follow it with `git push --force-with-lease` (never bare `--force`), and say so in your summary. When resolving `index.md`, verify the union — every side's entries present — and report the count.

**Commits on `main` are exceptional** (machine-branch topology): the pre-commit guard blocks them by design. When the user explicitly sanctions main work (`COMPENDIUM_ALLOW_MAIN=1`), the old rules apply: commit first, then `git fetch origin` and, if `origin/main` has advanced, `git rebase origin/main` (tree is clean now, so this is safe). Never push `main` directly — the pre-push guard blocks it; `main` advances via PRs. If a truly exceptional direct push is user-sanctioned, `--no-verify` with the sanction recorded in your summary.

### When to commit

- Completing an item (moves to resolved/completed dir)
- A batch of related frontmatter updates across multiple items (e.g., sync `date_updated` for a sprint)
- Intake of a new item with its source material
- Completing a project with all its sub-items
- A logical group of changes that are closely related

### How to group commits

| What's changed                         | Suggested commit scope                                            |
| -------------------------------------- | ----------------------------------------------------------------- |
| Template frontmatter schema changes    | Single commit for all `_templates/` + `.claude/instructions/*.md` |
| Batch `date_updated` sync (sprint/OWL) | One commit per type (bugs, features, tasks)                       |
| Intake — new item + source material    | One commit per item + its `_sources/` files                       |
| Moving completed items to resolved/    | One commit for all items in that batch                            |
| Cross-link updates, wikilink fixes     | One commit for the batch                                          |
| Mixed changes across types             | One commit per type                                               |

### Commit message format

`<type>: <short description>`

**Good commit messages:**

- `bugs: add date_updated to 14 active bugs (OWL-19455 batch)`
- `FEAT-016: add adhoc template research sources`
- `templates: add release_date, clickup_id/clickup_url frontmatter fields`
- `bugs/resolved: move completed bugs to resolved directory`

### Pre-commit hooks

Always run `pre-commit run --files $(git diff --name-only --cached)` before committing to ensure markdown and YAML files pass formatting and linting checks.

### Avoid

- Committing unrelated changes together (e.g., a new feature intake + a batch of unrelated bug updates)
- Over-granular commits (one file per commit when they're clearly related)
- Rebasing a feature/worktree branch onto `origin/main` — on every commit, _or_ reflexively at PR time. Open the PR as it stands and let GitHub judge mergeability; rebase only when asked or when the PR is actually blocked
- Resolving another session's `index.md` conflict unattended — a wrong union silently drops their entry. Check in instead
- Running `git rebase` with uncommitted changes — commit first, always

## Frontmatter YAML Gotchas

Four ways a frontmatter value silently breaks. `_scripts/lint-frontmatter.py` is the source of truth for which checks block commits (its module docstring lists them — unquoted-`#`, colon-space, body-leak, plus schema/status/completion-field/allow-list checks; leading-digit is the one below it does not yet catch) — this prose is belt to that lint's suspenders. Rule of thumb: **single-quote any string value containing `#`, `": "` (colon-space), or a leading digit.**

**1. Unquoted `#` → silent truncation.** An unquoted `" #"` (space-hash) starts a YAML comment, so `completed_in: compendium #69 + dotfiles #37` parses to just `"compendium"` — no error, wrong value. Single-quote it: `completed_in: "compendium #69 + dotfiles #37"`. `_scripts/complete-item.py` now auto-quotes refs, so prefer it for completions.

**2. Colon-space (`": "`) → parse break.** `retrieval_summary: Foo: bar` raises "mapping values are not allowed here" and breaks the whole block. Single-quote the value.

**3. Leading digit → numbered-list misparse.** If a string value begins with a digit (e.g., `8 of 10 questions`), YAML reads it as a numbered list and Obsidian frontmatter rendering breaks. Single-quote it, or for a multi-line field use a `>-` folded block scalar (never for `retrieval_summary`):

````yaml
status_detail: >-
8 of 10 design questions decided. 2 remain open for Joel:
  triggering mechanism (deploy-gate vs on-demand),
  pipeline automation (full fleet vs smoke suite).
```text

The `>-` folded block scalar produces a single logical line while avoiding the numeric-list ambiguity. See `.claude/instructions/projects.md` for the full list of fields affected.

**4. Body-leak past a mangled `---`.** If the closing `---` gets mangled, the H1 title and intro get absorbed into the frontmatter as junk keys (hit on PROJ-026/TASK-101), and `lint-frontmatter.py`'s required-key checks still pass. The malformed-key check (**fatal**) now catches it — keep a clean `---` on its own line closing the block.

## Worktree & Branch Conventions

**For longer-running compendium updates and research sessions, use Claude Code worktrees.** A worktree gives the session its own isolated working tree backed by a real git branch — safe from interruptions, crash-resilient, and mergeable back into `main` when done. This is the default for any task that touches more than a few files or spans an extended period (multi-item intake batches, project completions, deep research docs, plan creation, skill development).

**Merge back to the machine branch**: Worktree branches base on and merge back into the **machine branch** (`pop`/`workbook`) when they're done — the repo's `worktree.baseRef: head` setting makes `EnterWorktree` branch from it automatically; their content reaches `main` at the next compaction PR (PROJ-1017). Use `EnterWorktree` with `action: "keep"` at the end of a session and let the user review; use `action: "remove"` once the changes are committed and merged, then finish the post-merge cleanup procedure below — merging without cleaning up is an unfinished session.

**When NOT to use a worktree**:
- Simple single-item edits (one bug fix, one status transition) — just commit directly on the machine branch (`pop`/`workbook`) in the shared checkout.
- Read-only operations (querying, linting, searching).
- When the user asks for a specific branch name instead.

For other repositories (dipdash, mage, dotfiles, etc.) that have their own worktree conventions, follow those repos' rules. The restriction above applies only to `~/code/compendium/`.

Branches follow an `OWL-NNN/kebab-slug` format, e.g. `OWL-19576/source-file-names-improvements`.

### Post-merge cleanup is mandatory

A merged branch or worktree left behind is not "done" — stale branches accumulate, confuse later sessions and cron runs, and defeat the one-branch-per-run rules below. Every session that merges a branch cleans up **in the same session**, before reporting the work complete:

1. **Verify the merge actually landed** before deleting anything. For local merges, confirm the merge commit is on **the branch that received the merge** — the machine branch (`pop`/`workbook`) for worktree branches; `main` only for compaction/cron PRs. For PR merges, confirm with `gh pr view <N> --json state,mergedAt`. **Squash-merge caveat**: a squash-merged branch's tip is *never* reachable from `main`, so reachability checks (including `git-guard safe-branch-delete`) refuse even though the content is fully merged — this is the known IMPR-1060 gap. There, the merge evidence is `gh pr list --state merged --head <branch>`, not reachability.
2. **Remove the worktree**: `ExitWorktree` with `action: "remove"` (or `git worktree remove <path>`), then `git worktree prune`.
3. **Delete the branch** — local via `git-guard safe-branch-delete <branch>`, remote via `git push origin --delete <branch>`. If `safe-branch-delete` refuses on a branch that step 1 proved squash-merged, deleting anyway is sanctioned **only with that `gh` evidence recorded in your session summary** — say explicitly which branch was deleted and what proved the merge.
4. **End-of-session sweep**: run `git worktree list` and `git branch --list`. Any leftover branch/worktree you created must be either cleaned up or explicitly reported as intentionally kept (e.g. `EnterWorktree action: "keep"` pending user review) — never left behind silently.

The only branches that may outlive a session are ones the user is still reviewing; name them in your summary so the next session knows they're live, not stale.

### Shipping a `compendium-*` skill change

Skill changes span two repos. The end-to-end flow — the repo split (vault instructions/scripts vs `dotfiles` skills) and the **dual-copy sweep** (every `compendium-*` skill lives twice: `dotfiles/claude/skills/` **and** `dotfiles/hermes/skills/claude/skills/` — edit both, confirm parity with `diff -q`) — is documented in [`GUIDE-022`](guides/tooling/GUIDE-022-compendium-shipping-skill-changes-end-to-end.md). **Shipping ends when both halves land on `main`**; the MacBooks go live from there via the `~/.claude/skills` symlink. Bringing the `timmy` homelab node current is an optional follow-up (GUIDE-022 Step 4), not a gate — a `timmy` that is behind is not an unfinished ship. Authoring invariants, incl. the dual-copy rule and advisory-first check rollout, are in [`GUIDE-021`](guides/tooling/GUIDE-021-compendium-authoring-standard.md) A5.

### Cron job branch isolation

Cron jobs that modify the compendium (vault health scan, link integrity, research sweep, dipdash/mage scans) must follow these rules to prevent branch conflicts. **These jobs run on the hermes cluster against its own clone, where `main` remains the correct base** — cluster jobs integrate PR-mediated into `main`, which is allowed (the machine-branch topology reserves *direct pushes and day-to-day commits* for machine branches; PRs into `main` are the sanctioned advance path). A cron job must **never run on a machine's shared checkout** — flipping that checkout's branch would silently retarget the machine's session commits.

1. **Always `git checkout main && git pull` before creating a branch** (in the cluster clone). Never branch from a stale main.
2. **Never use `git checkout -b` while another branch is checked out.** Return to main first, pull, then branch.
3. **One branch per cron run.** If a previous run's branch still exists (e.g. `vault-health-2026-06-29`), delete it before creating a new one: `git branch -D <old-branch>`.
4. **Schedules are staggered** so no two compendium-modifying jobs run simultaneously:
   - Vault health scan: Monday 9:00
   - Vault link integrity: Monday 10:00 (after health scan finishes)
   - Research sweep: Tuesday 11:00 (different day entirely)
   - DipDash/Mage health scan: Sunday 6:00
   - DipDash/Mage refactor sweep: Sunday 7:00
5. **Clean up after PR merge — in the same run, not "eventually".** Follow the full post-merge cleanup procedure above (verify merge → remove worktree → delete local **and** remote branch → `git checkout main && git pull`). A run that ends with its merged branch still present has not finished; rule 3's pre-run delete is a backstop for crashed runs, not the normal cleanup path.

### Concurrent interactive sessions

Multiple sessions/agents can run against the shared `~/code/compendium` working tree at once — all committing to this machine's branch (`pop`/`workbook`), which the shared checkout keeps checked out. Same-machine contention is unchanged by the machine-branch topology; what the topology removes is **cross-machine** contention (the other machine writes to its own branch, and the curated indexes reconcile at compaction time). Sessions contend on the shared `index.md` files (the hand-maintained `log.md` operations logs were dropped in IMPR-1092 — the operations log is git history now), and a commit in one session can sweep up another's **uncommitted** edits to those files. The procedure:

- **Stage specific files, never `git add -A`,** when another agent may be active — so you neither absorb a neighbor's in-flight edits nor get swept into theirs.
- **Commit first, reconcile second.** Get your own work committed before any sync operation; never "clean up" the tree to make a sync work — an unexpected dirty path is probably a concurrent session's in-flight work, not yours to discard.
- **Reconcile, don't force.** If a push is rejected, `git pull --rebase origin <machine-branch>` and re-push; a rebase usually **auto-unions** competing `index.md` edits cleanly — verify the union (both sessions' entries present) after resolving. Never resolve contention with `reset --hard`/`checkout --`/`stash drop` in the shared checkout — the PreToolUse hook blocks these; use the `git-guard` equivalents (next section).
- **Branch work happens in a worktree.** Needing a clean tree while the shared checkout is dirty is the signal to `git worktree add`, not to clean the shared tree.
- The durable fix for the remaining `index.md` contention is deterministic index generation — tracked in [[IMPR-1050-other-derived-index-log-generation]].

For bulk frontmatter edits across many items, use the subagent bulk-edit pattern in [[GUIDE-021-compendium-authoring-standard|GUIDE-021]] A7.

### Destructive git operations are guarded (IMPR-1056)

**History surgery happens in a worktree; the shared checkout only advances via commit/pull.** A PreToolUse hook blocks the destructive-command class (`reset --hard`, `clean -f`, `checkout -- <path>`, `restore <path>`, `stash pop|drop`, `branch -D`, bare `push --force`) whenever the command targets `~/code/compendium` — because a concurrent session may hold uncommitted work the command would destroy (the 2026-07-12 incident). When you legitimately need one of these, use the recoverable `git-guard` equivalent (`git-guard clean-tree` / `safe-reset` / `safe-branch-delete`, in `~/.local/bin/`) — its checks test output emptiness and commit reachability, never exit codes — or do the operation on a worktree branch and merge back.

## General rules for editing live configs

Several directories in this repo are symlinked to live runtime locations (`~/.config/<name>`, `~/.hermes/`, `~/.claude/`, etc.). An edit here is an edit to a running tool's config. Follow these rules:

1. **Know what's live.** Before editing any file under `hermes/`, `claude/`, or `obsidian/`, check whether it's symlinked to a runtime path. Run `ls -la ~/.hermes/config.yaml ~/.claude/settings.json ~/code/compendium/.obsidian/` to see what's live.

2. **Only perform mass reformatting with explicit permission.** Do not run `pre-commit run --all-files`, `yq -i -P`, `prettier --write`, or any bulk formatter on `hermes/config.yaml`, `claude/settings.json`, or `obsidian/*.yaml` unless the user explicitly asks for it. The 2026-06-29 config corruption started when a bulk format pass appended unrelated YAML into `hermes/config.yaml`.

3. **No bulk renames or restructures of symlinked directories.** `hermes/skills/`, `claude/skills/`, and `obsidian/` are all symlinked to live locations. Renaming or moving files there breaks running agents, cron jobs, and Obsidian plugins.

4. **Validate before committing.** For YAML configs: `uv run --with pyyaml python3 -c "import yaml; yaml.safe_load(open('path/to/file.yaml').read())"` (system `python3` has no PyYAML). For JSON configs: `python3 -c "import json; json.load(open('path/to/file.json'))"`. If validation fails, revert — do not commit broken configs.

5. **Prefer targeted edits over wholesale replacements.** When adding a setting, add only the new key. When changing a value, change only that line. Avoid reformatting surrounding content.

### opencode (`opencode/`)

The local-model coding harness. `opencode.jsonc`, `tui.json`, `AGENTS.md` and the `themes/`, `commands/`, `agents/` directories are symlinked into the real `~/.config/opencode/` (opencode writes plugin `node_modules/` there, so the directory is never replaced). `model` and `small_model` both pin `qwen3.6:coding-35b` as of

and local Claude Code on one tag. Bare Pi is deliberately cloud-default as of

no-pin/picker arrangement was
reversed because picking a different tag evicts the resident model and its

losing harness (IDEA-1085). `ocg()` still reaches `gemma4:coding-26b`

Parity with the Claude Code config is deliberate, and stops in three specific places:

| Claude Code                         | opencode                                    | Note                                                        |
| ----------------------------------- | ------------------------------------------- | ----------------------------------------------------------- |
| `theme: custom:aura`                | `theme: aura` → `opencode/themes/aura.json` | Hand port — the two theme schemas share no key names        |
| `commands/*.md`                     | `commands/*.md` (`commit`, `describe_pr`)   | Commands cost **zero prefill** until invoked, unlike skills |
| `agents/*.md` subagents             | `agents/review.md` as a **primary** agent   | `permission.task` stays denied; primaries are unaffected    |
| `preferredNotifChannel: ghostty`    | `tui.json` → `attention.enabled`            | Off by default upstream; a local turn runs for minutes      |
| `editorMode: vim`                   | —                                           | No counterpart: "vim" appears 0× in the tui schema          |
| On-demand docs (`TOOL_USAGE.md`, …) | —                                           | `instructions` is **always** injected; see below            |

Three more traps, on top of the six recorded below:

7. **`tui.json` is a second config file**, with its own schema — `theme`, keybinds, `attention`, `diff_style`. Keys put in the wrong file load without complaint and do nothing. **`theme` is the one that bites**: with `"theme": "aura"` in `opencode.jsonc`, `opencode debug config` reports `theme: null`. It is plain JSON; only `opencode.jsonc` takes comments.
8. **Never add `instructions`.** It looks like the analog of the on-demand reference-doc table in `claude/CLAUDE.md`, but every listed file is injected into every prefill — the exact cost this config exists to avoid, with no lazy-load alternative while `permission.skill` is denied.
9. **The three config files merge, they do not shadow.** opencode loads `config.json`, `opencode.json`, then `opencode.jsonc` and later wins on conflicts (each gets a `loading path=` line in `~/.local/share/opencode/log/opencode.log`). An earlier comment in `install.sh` claimed a stray `opencode.json` would win outright — wrong, but the split is still how the claude-mem `plugin` key went untracked. Keep every authored key in `opencode.jsonc`.

10. **`plugins/`, `commands/`, `agents/` and `themes/` are auto-discovered** — a file dropped in `~/.config/opencode/plugins/` is picked up with **no config key naming it**. `opencode debug config` lists `plugins/claude-mem.js` with no `plugin` key present at all. Deleting the file, not removing a key, is what unregisters a plugin.

The claude-mem plugin **works** (verified 2026-07-30). It previously failed every startup with `Plugin export is not a function`; the obvious suspect was the `@opencode-ai/plugin` 1.16.2 pin against a 1.18.x runtime, but that was wrong — reinstalling the plugin fixed it with the pin unchanged. It was a stale build artifact.

11. **`opencode run` blocks on stdin when stdin is an open pipe.** Any non-interactive caller that leaves stdin open — the Claude Code Bash tool, a cron job, CI — hangs forever with **zero output and no error**, even though the model finished. Measured 2026-07-30: identical prompts took 12s with `</dev/null` and never returned without it. The session is written to the DB either way, so `opencode debug config`-style forensics show a completed turn while the process sits there.

    **Always redirect stdin for scripted runs:** `opencode run "…" </dev/null`. Diagnose a suspected hang by checking whether it ever opened a socket to the model (`lsof -nP -iTCP:11434`) — if not, it never reached inference.

12. **A tool-level `deny` is not a capability deny while `bash` is reachable.** The `review` agent originally paired `edit: deny` with `bash: allow`. Told to delete a function, the model hit `Model tried to call unavailable tool 'edit'` and then ran `sed -i` to do it anyway — successfully, then reported it as done. Any read-only agent must pattern-scope `bash` (`"*": deny` plus an explicit allowlist), not merely deny the write tools. Re-verified after the fix: the bypass is refused and the model says so.

Verifying this config, in decreasing order of how much they prove:

| Command                                             | Proves                                                         |
| --------------------------------------------------- | -------------------------------------------------------------- |
| `opencode debug config` — **see the warning below** | Resolved config — the only way to catch a silently-dropped key |
| `opencode agent list`                               | Agents registered                                              |
| `opencode run "…" </dev/null`                       | Plugins actually load (see the false negatives below)          |

All are headless — none costs a model call.

⚠ **`opencode debug config` prints resolved secrets.** It expands `${VAR}` from the
environment, so `mcp.*.headers.Authorization` and any credential env var appear in
full in its output — and therefore in any captured agent transcript or CI log.
Never run it bare where output is recorded. Pipe it through a redactor:

```bash
opencode debug config | python3 -c 'import json,sys,re; print(re.sub(r"(Bearer |\"[A-Z_]*KEY\": \")[^\"]+", r"\1[REDACTED]", sys.stdin.read()))'
```

⚠ **Plugin-load checks give false negatives.** `opencode serve` and a direct
`bun -e 'await import(...)'` both succeed against a plugin that opencode rejects,
because the loader validates **every** module export, not just `default`. Use a
real `run`, and note a _healthy_ load emits no log line — an empty grep proves
nothing on its own.

Narrow by default, the same way `lclaude()` is for Claude Code — prefill is the scarce resource on a local 26B. Measured on opencode 1.18.9 by pointing the shipped config at a mock OpenAI-compatible server and capturing its outbound HTTP body (2026-07-29): **~17.8k → ~7.4k tokens, 58.3% smaller**.

| Trim                                    | Saves         | Where            |
| --------------------------------------- | ------------- | ---------------- |
| `permission: {skill: "deny"}`           | ~4.6k tok     | `opencode.jsonc` |
| `permission: {task: "deny"}`            | ~964 tok      | `opencode.jsonc` |
| `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT=1` | ~5.4k tok     | `zsh/.zshrc`     |
| All 10 MCP servers `enabled: false`     | schema + init | `opencode.jsonc` |

Six things here are easy to break and were established by measurement, not docs:

1. **Thinking suppression needs camelCase `options.reasoningEffort: "none"`** — opencode translates it to `reasoning_effort` in the body, the only field Ollama 0.32.5 honors on `/v1/chat/completions` (the surface opencode uses). Snake_case `reasoning_effort` in config is silently dropped.
2. **`"reasoning": true` is required, but only safe when paired with an explicit effort.** On its own it makes opencode inject `reasoning_effort: "low"` — thinking ON. Alongside `options.reasoningEffort` it's both safe and necessary: without it opencode _discards_ the response's reasoning field, so asking for thinking costs 3.5–5.5× the completion tokens and displays nothing.
3. **A `permission` deny removes the tool's schema from the request**, not just the ability to call it — that is why the denies above are a prefill lever. Same technique as `claude/settings-local-model.json`.
4. **`~/.config/opencode/AGENTS.md` does NOT displace `~/.claude/CLAUDE.md`** despite opencode's docs saying it takes precedence. Measured additive; only the env var drops it.
5. **The schema key names are singular.** The config page's schema index lists section headings (`permissions`, `mcp-servers`, `formatters`, `sharing`, `models`); the literal keys are `permission`, `mcp`, `formatter`, `share`, `model`. A config written from that index loads without complaint and does nothing.
6. **`formatter` omitted means all formatters off**, and `formatter: true` is conditional per built-in — each fails silently when its requirement is unmet. Prettier only activates when the project has prettier in `package.json`, so it does **not** fire in this repo; `opencode/AGENTS.md` still carries the formatter rule for markdown/JSON here.

`small_model` is deliberately the same model as `model`: with `OLLAMA_MAX_LOADED_MODELS=1`, a different small model evicts and reloads the resident 27 GB primary on every session-title generation.

**Permissions are fully permissive** — the equivalent of Claude Code's `--dangerously-skip-permissions`, matching how `lclaude()` runs. Two guards are therefore disarmed on purpose: `.env` reads (opencode's default denies them) and `external_directory` (which had caught the 26B retyping a path as `/Users/noat/...`). Both restore in one line; see the comments in `opencode.jsonc`. The only remaining denies are `skill`/`task`, which are prefill levers, not safety settings.

Shell surface in `zsh/.zshrc`: the two `OPENCODE_DISABLE_CLAUDE_CODE_*` env flags, plus `oc` (interactive; now opens on the pinned `qwen3.6:coding-35b` rather than the picker), `ocr` (one-shot via `ollama launch`), `ocg` (pinned to `gemma4:coding-26b`), and `occ`/`ocm`/`ocstat`. The model-switch, thinking-debug, and warmup aliases were trimmed 2026-08-01; thinking checks go through `opencode run --thinking 'say OK' </dev/null` (a `run`-only flag — the TUI has no equivalent, so there is no `ocr` form) and `--variant low|medium|high|max` to turn thinking on per invocation.

Full per-surface thinking matrix: `claude/GUARDRAILS.md` §1. Vault entries: INFO-1134 (thinking matrix), INFO-1135/INFO-1136 (opencode config + extensibility), GUIDE-1076 (setup procedure).

### Hermes (`hermes/`)

Config for the Hermes AI agent. Only authored config is tracked (config.yaml, SOUL.md, hooks, skins, skill definitions). Runtime state (state.db, sessions, logs, secrets) lives in the real `~/.hermes/` directory, never in git.

**⚠️ CRITICAL: `hermes/config.yaml` is a live runtime config.** It is symlinked to `~/.hermes/config.yaml` which Hermes reads on every turn. Non-Hermes agents (Claude Code, Codex, etc.) must follow these rules:

1. **Never run `hermes config set`, `hermes doctor --fix`, or any Hermes CLI command.** These mutate the live config and can break the running Hermes instance. Only Hermes itself should invoke these.

2. **Never append unrelated YAML documents to `hermes/config.yaml`.** The file must contain exactly one YAML document. A second `---` separator followed by unrelated content (pre-commit config, GitHub PR sections, etc.) makes the file unparseable by `yaml.safe_load()`, causing Hermes to fall back to defaults and lose all provider/auxiliary config. This is what caused the 2026-06-29 config corruption (commit `1147dfd`).

3. **Only make targeted, minimal edits to `hermes/config.yaml` when explicitly asked.** Do not reformat, reflow, or restructure the file. The Hermes config parser is sensitive to YAML formatting changes (personality strings, empty-value quoting, etc.).

4. **Validate YAML before and after any edit.** Run `uv run --with pyyaml python3 -c "import yaml; yaml.safe_load(open('hermes/config.yaml').read())"` (system `python3` has no PyYAML) to confirm the file parses as a single document. If it fails, revert your change immediately.

5. **`hermes/skills/` is also a live symlink target.** Do not mass-edit, rename, or restructure skill directories unless you are a Hermes agent or explicitly asked. Cron jobs depend on skill names resolving directly in `~/.hermes/skills/`.

# Guardrails for local Qwen agents

Behavioral constraints and compensating controls for Qwen 3.6 models running locally through Pi or Ollama. These are model-level limitations that require deterministic workarounds, not prompt engineering.

## 1. Thinking suppression

Qwen3.6 local models advertise the `thinking` capability in Ollama. Ollama auto-enables thinking by default, which can cause empty visible responses, length stops, garbled output, and write-repair loops when the client does not hard-disable thinking.

**Hard-disable thinking at the API boundary; prompt text alone is not enough:**

| Layer                                | Mechanism                                              | What it guarantees                                               |
| ------------------------------------ | ------------------------------------------------------ | ---------------------------------------------------------------- |
| Native Ollama `/api/chat`            | `think: false` (boolean) at request-body **top level** | Tells Ollama not to enable thinking mode                         |
| Ollama Anthropic `/v1/messages`      | `thinking: {"type": "disabled"}`                       | Disables Anthropic-compatible thinking blocks                    |
| Ollama OpenAI `/v1/chat/completions` | `reasoning_effort: "none"`                             | The only lever that works on this surface (0.32.5+ — see below)  |
| Modelfile / template                 | ✗ nothing — no model-level suppression exists          | Not a control point at all; see "Modelfile cannot do this" below |
| Proxy                                | `ollama-thinking-proxy` on port 11435                  | Injects the correct field per surface on all three (see below)   |

⚠ `think` goes at the **top level** of the request body, never inside `options` — misplacing it is ERR-1004, where the model burns its whole token budget on reasoning and returns empty content.

⚠ **The fields are not interchangeable, and the wrong one fails silently.** Each surface honors exactly one; a mismatch returns HTTP 200 with thinking still on rather than an error. Measured 2026-07-29 on `gemma4:coding-12b`: `reasoning_effort:"none"` on `/api/chat` → 510 chars of thinking; `think:false` on `/v1/chat/completions` → 360 chars; `think` nested in `options` → 671 chars. That silence is what let the proxy's OpenAI-path suppression sit dead for three weeks.

**The OpenAI path became fixable in 0.32.5 — use `reasoning_effort: "none"`.** This supersedes the previous "OpenAI-path clients cannot be made safe" finding (INFO-1089, verified 2026-07-07 against 0.31.1), which held that `/v1/chat/completions` was unusable for write agents. Re-verified 2026-07-29 on pop against Ollama **0.32.5**, three tags (`gemma4:coding-12b`, `gemma4:coding-26b-mxfp8` — named `gemma4:coding-26b` at the time, renamed 2026-08-02 — `qwen3.6:coding`), identical results on all three:

| Field on `/v1/chat/completions`               | Result                                     |
| --------------------------------------------- | ------------------------------------------ |
| `reasoning_effort: "none"`                    | ✅ reasoning length → 0                    |
| `think: false`                                | ❌ still a no-op (unchanged from 0.31)     |
| `chat_template_kwargs: {enable_thinking:...}` | ❌ no-op                                   |
| _(no flag)_                                   | reasoning emitted — thinking is default-on |

Practical consequence: OpenAI-compatible clients (Zed, opencode, most SDKs) are now safe on this surface **provided `reasoning_effort: "none"` is sent** — either by the client itself or by the proxy.

**opencode specifically** (`opencode/opencode.jsonc`, measured by capturing its outbound body on 1.18.9): the field it sends is controlled by **camelCase `options.reasoningEffort: "none"`** on the model entry. Two traps, both silent:

| In `opencode.jsonc`                             | Lands in the body as                     |
| ----------------------------------------------- | ---------------------------------------- |
| `options.reasoningEffort: "none"` ✅            | `reasoning_effort: "none"`               |
| `options.reasoning_effort: "none"` (snake_case) | nothing — silently dropped               |
| `"reasoning": true` with no recognized effort   | `reasoning_effort: "low"` ⚠ thinking ON |

So snake_case looks right and does nothing, and `"reasoning": true` on its own actively enables thinking. But **paired with an explicit `reasoningEffort` it is required**: without it opencode discards the `reasoning` field from the response, so thinking-on costs 3.5–5.5× the completion tokens and renders nothing. The shipped config sets both — default `none`, plus `variants` so `--variant low|medium|high|max` turns it on per invocation.

⚠ **On gemma4 the effort LEVEL is inert.** Ollama validates the value (only `none`, `low`, `medium`, `high`, `max` — OpenAI's `minimal`/`xhigh` are HTTP 400) but the model does not act on the gradation. Measured 2026-07-30, 3 reps each on `gemma4:coding-26b-mxfp8` (named `gemma4:coding-26b` at the time, renamed 2026-08-02): `low` ~2630, `medium` ~2606, `high` ~2610, `max` ~2514 chars of reasoning — all means within 4.4%, with ~400 chars of within-group spread. Treat it as on/off, not a dial.

Verify with `opencode run --thinking 'say OK' </dev/null`, which _shows_ reasoning rather than enabling it (confirmed: prints nothing while suppression holds). If that prints a `Thinking:` block, the config has regressed. This line read `ocr --thinking` until 2026-08-03 and was unrunnable three ways: `ocr()` discarded its arguments (fixed the same day); `ocr` launches the **TUI** through `ollama launch`, and `--thinking` exists only on `opencode run`, not on the TUI; and the parenthetical claimed a bare `opencode run` has no model — true only between the 2026-08-01 picker change and 2026-08-03, when `model` was pinned to `ollama/qwen3.6:coding-35b`. There is no `ocr` form of this check; use `opencode run` directly.

**The proxy now injects it (fixed 2026-07-29).** Until then `ollama-thinking-proxy` injected only `think: false` on `/v1/chat/completions`, which is a no-op there — so its OpenAI-path suppression had been silently dead since 0.31, while the startup banner still announced it. That mattered: `hermes/skills/pi/agent/models.json` pointed an `openai-completions` provider at `11435/v1` with the `homework-*` and `qwen3.6:27b-q4_K_M` models, relying on suppression it was not getting. (That file was deleted 2026-07-31 as an inert twin — it is the historical victim of this bug, not a current consumer. The proxy's live consumer is pi's `ollama-pop` provider in `pi/agent/models.json` — `ollama-homelab` was removed 2026-08-01.) Two changes:

| Change                | Detail                                                                                                                                                                                                           |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Correct field         | `/v1/chat/completions` gets `reasoning_effort: "none"`. `think: false` is still sent alongside — a no-op today, kept only so a future Ollama honoring it sees a consistent instruction.                          |
| Pattern-based matcher | The old flat list of exact names had stopped covering the tags in use — `gemma4:coding-*` and `qwen3.6:coding` matched nothing and passed through with thinking on. Now glob patterns over local model families. |

Cloud tags (`*:cloud`) are deliberately exempt and keep their reasoning: forcing reasoning off on a hosted reasoning model is an error or a capability downgrade, not a fix. `THINK_OFF_EXTRA="foo:*,bar"` adds patterns without editing the script. Covered by `tests/test-ollama-thinking-proxy.sh` (36 assertions, offline against a mock upstream — no Ollama or GPU needed).

**Modelfile cannot do this — it is not a weak control, it is not a control.** `PARAMETER think false` is rejected outright (`Error: unknown parameter 'think'`, 0.32.5). Nor can a `TEMPLATE` override with a `/no_think` suffix help for newer model families: `ollama show --template gemma4:coding-12b` returns bare `{{ .Prompt }}` because gemma4 uses a **built-in Go renderer** in 0.32, so there is no template for a Modelfile to intercept and the thinking control token is emitted by the server purely from the request field. Suppression is request-level or it does not happen.

## 2. Tokenizer whitespace bugs

Qwen 3.x has tokenizer-level bugs that corrupt whitespace. These are not fixable by prompt engineering.

| Symptom                                | Root cause                              | Risk                     |
| -------------------------------------- | --------------------------------------- | ------------------------ |
| Extra spaces inside `{}` in f-strings  | Tokenizer boundary bug on `{`/`}`       | SyntaxError, broken URLs |
| Spaces around hyphens in file paths    | Tokenizer mis-handling `-` boundaries   | File-not-found errors    |
| Tab characters in JSON output          | Tokenizer decoding `\\t` as literal tab | Invalid JSON             |
| Garbled whitespace under `json_schema` | Unknown (reproducible after ~10 calls)  | Blank/spam output        |

**Bounded formatter workflow** — format/check after every Write or Edit, but never loop:

| File type             | Formatter | Command                       |
| --------------------- | --------- | ----------------------------- |
| Python                | ruff      | `uv run ruff format <file>`   |
| Markdown              | prettier  | `npx prettier --write <file>` |
| JavaScript/TypeScript | prettier  | `npx prettier --write <file>` |
| JSON/YAML             | prettier  | `npx prettier --write <file>` |
| Go                    | gofmt     | `gofmt -w <file>`             |
| Rust                  | rustfmt   | `rustfmt <file>`              |
| Shell                 | shfmt     | `shfmt -w <file>`             |
| SQL                   | sqlfluff  | `sqlfluff fix <file>`         |

After a failed format/check, make one minimal repair patch and run the check one more time. If it still fails, stop and report the exact output. Whole-file rewrite loops are forbidden for Python and YAML indentation repairs.

**Rationalization patterns that will fail:**

- "The indentation looks correct to me" — tokenizer can corrupt it silently
- "I'll match surrounding indentation by hand" — Qwen's tokenizer doesn't model indentation consistently
- "Let me re-read and fix whitespace" — you'll produce different corruption
- "This is a one-character fix, no formatter needed" — one-character changes trigger the same bugs
- "I'll use a heredoc for exact whitespace" — heredocs route through the same tokenizer
- "I need to rewrite the file to fix indentation" — rewriting preserves the same bugs. Use Edit + formatter.

## 4. Deterministic preflight pattern (IDEA-1006)

The reliability of a small-model agent is determined by **how little judgment you ask of it**, not by model size. Push all filtering and safety decisions into deterministic bash preflight, not into the model prompt.

| Layer | Runs on             | Mechanism                                           | Guarantee                                                 |
| ----- | ------------------- | --------------------------------------------------- | --------------------------------------------------------- |
| 1     | bash (no LLM)       | Regex deny-list of unsafe file patterns             | Model never sees secrets, binaries, build artifacts       |
| 2     | bash (no LLM)       | `.gitignore` parsing + glob-to-regex conversion     | Ignored files excluded deterministically                  |
| 3     | git itself          | `.git/info/exclude` shield                          | Model cannot stage unsafe files even with `git add .`     |
| 4     | LLM (system prompt) | "Don't re-discover" instruction, explicit adds only | Model writes commit messages, doesn't reason about safety |

This pattern generalizes beyond git commits: any LLM agent task benefits from deterministic preflight filtering that removes unsafe/irrelevant material before the model sees it.

## 7. Monitoring the server (`ollama-logs`)

To check whether Ollama is actually handling requests — is a model loaded, is a request in-flight, did it error, is prefill stalled vs. progressing — use **`ollama-logs`** (aliases `ologs` / `ollogs`; script at `~/.local/bin/ollama-logs`, from `~/code/dotfiles/bin/`). It classifies each log line and, by default, drops the per-batch progress spam while keeping actionable signal.

**Which files it reads (layout auto-detected by mtime, newest wins):**

| Layout                                | File(s)                                                                       | Carries                                                                            |
| ------------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Headless LaunchAgent (canonical)      | `/tmp/com.user.ollama-serve.err.log` **and** `/tmp/com.user.ollama-serve.log` | stderr: runner subprocess + prefill/cache/memory · stdout: the public `:11434` API |
| Native Ollama.app (fallback/historic) | `~/.ollama/logs/server.log` (+ rotated `server-N.log` with `-a`)              | one interleaved stream                                                             |

**⚠ Under the LaunchAgent, both streams are required — they are disjoint.** The split is **by which server handled the request, not by URL prefix** — `/v1/` appears in both files meaning different things:

| Stream                 | Server                                     | Paths                                                                                      |
| ---------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------ |
| stdout `[GIN]`         | public, `[::]:11434`                       | all `/api/*` **and** the compat endpoints `/v1/messages?beta=true`, `/v1/chat/completions` |
| stderr `msg=ServeHTTP` | runner subprocess, `127.0.0.1:<ephemeral>` | `/v1/status`, `/v1/completions`, `/v1/tokenize` — and nothing else                         |

So `/v1/messages` (**Claude Code's own endpoint**) is public and lands in **stdout**, while `/v1/completions` is the runner's internal call and lands in **stderr**. Not one `/api/*` path is present in stderr — 0.32.x did _not_ move public access logging into the structured logger. The runner's port changes on every model load, which is the reliable tell that those lines are not the public server. The tool merges both chronologically. An earlier revision read stderr alone on the belief stdout was dead, which reported the runner's internal traffic as though it were the server's and hid every user-facing request and 5xx. Full topology: `~/code/compendium/info/ollama-serving/INFO-1133-dotfiles-ollama-log-stream-topology-on-pop-two-disjoint-launchd-strea.md`.

**Known gap:** `perf` reports the _runner's_ request time, not the public request's — its gate admits only structured `ServeHTTP` rows matching `completions|generate|chat|embed`, which excludes Gin rows entirely and does not match `/v1/messages`. Take wall time for Claude Code requests from `requests` mode instead.

Picking the layout by mtime means the tool self-corrects across migrations rather than silently tailing a file nothing writes any more — the failure mode when the app was retired on 2026-07-28 and `server.log` kept "working" while showing day-old data. If the selected files have gone quiet, the script probes `:11434` and warns **only when its own probe fails to land in one of them** — quiet logs alone are not evidence of a wrong file, since an idle server is quiet too. Override with `OLLAMA_LOG_FILE=<path>` (exact file) or `OLLAMA_LOGS_DIR=<dir>` (forces the app layout).

The script forces `LC_ALL=C` internally: every GGUF load dumps a BPE merge table that is truncated mid-character, and in a UTF-8 locale macOS awk aborts on it (`towc: multibyte conversion failure`, exit 2) after printing only the lines _before_ the bad byte — hiding the newest data behind output that looks complete. If you pipe this tool's output into your own `awk`, set `LC_ALL=C` there too.

**Agent usage — always non-interactively** (no `-f`; add `-C` when capturing to avoid ANSI codes, `-q` to drop the source banner):

| Question                                   | Command                         |
| ------------------------------------------ | ------------------------------- |
| Is it serving / did the last request fail? | `ollama-logs requests -n 50 -C` |
| Any errors or non-2xx recently?            | `ollama-logs errors -a -C`      |
| Is a model loaded / what loaded?           | `ollama-logs events -n 400 -C`  |
| Prefill throughput, cache reuse, peak mem  | `ollama-logs perf -n 500 -C`    |
| Everything meaningful (default)            | `ollama-logs -n 200 -C`         |

**Reading it:** HTTP lines only appear when a request **completes** — an in-flight prefill shows no request line yet, so a "quiet" `requests` view during a long-context load is normal, not a hang. To confirm prefill is _advancing_ rather than stalled, read the `prefill N / M` lines in `signal` or `perf`: the processed count climbs per 2048-token chunk, and the derived `tok/s` is measured from the opening `cache` line. The `cache … % reuse` line is prefix-cache effectiveness — a sudden drop to low reuse explains a request that suddenly got slow.

Because both streams are merged, **one client request usually produces two rows**: the public `/api/*` line and the runner's `/v1/completions` line that served it, at nearly the same timestamp. Read the `/api/*` row as the user-visible outcome and the `/v1/*` row as the runner's view — a `500` on `POST /api/generate` with a clean `/v1/completions` above it means the failure was in the server, not the model. A `4xx` is a rejected/malformed request (surfaced by `requests` and `errors`), distinct from a model fault.

**⚠ Decode throughput is unavailable on the MLX engine.** The legacy llama.cpp runner emitted `slot print_timing … tokens per second` for both prompt-eval and eval; the `--mlx-engine` runner emits neither an equivalent nor a completion-token count, so decode tok/s can be neither read nor derived from these logs. `perf` reports what is measurable: prefill tok/s, request wall time, cache reuse, and peak memory. Do not report a decode rate from this tool — if a caller needs one, time a request against a known output-token count instead.

**Never** launch `-f` (live-tail) from an agent — it never returns. Use a bounded `-n`.

# Qwen agents — known issues and mitigations

The Qwen 3.x model family has known **tokenizer-level whitespace bugs** that cause indentation corruption when writing files. These instructions override any conflicting guidance from `CLAUDE.md` or `FORMATTING.md`.

## Known Qwen whitespace bugs

| Symptom                                             | Root cause                               | Risk                               |
| --------------------------------------------------- | ---------------------------------------- | ---------------------------------- |
| Extra spaces inserted inside `{}` in f-strings      | Tokenizer boundary bug on `{`/`}` tokens | SyntaxError in Python, broken URLs |
| Spaces around hyphens (`-`) in file paths           | Tokenizer mis-handling `-` boundaries    | File-not-found errors              |
| Tab characters (`\t`) injected into JSON output     | Tokenizer decoding `\\t` as literal tab  | Invalid JSON                       |
| Intermittent garbled whitespace under `json_schema` | Unknown (reproducible after ~10 calls)   | Blank/spam output                  |

**These are model-level bugs, not something you can think your way around. You must compensate with process.**

## API-level thinking suppression is mandatory

`/no_think` and this file are **not sufficient** to keep Qwen3.6 write agents stable. Local probes against `qwen3.6:35b-mlx` showed:

| Client surface                       | Required hard-disable                                                                                                                                                                                   |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ollama native `/api/chat`            | top-level `"think": false`                                                                                                                                                                              |
| Ollama Anthropic `/v1/messages`      | `"thinking": {"type": "disabled"}`                                                                                                                                                                      |
| Ollama OpenAI `/v1/chat/completions` | `"reasoning_effort": "none"` — works as of Ollama 0.32.5 (INFO-1134). `think:false` and `enable_thinking:false` are still ignored here, so the older "do not use this surface" advice no longer applies |

If a Qwen3.6 agent emits empty output, garbled output, or loops on writes, first verify the request path is actually hard-disabling thinking. Do not try to solve thinking-budget exhaustion with more prompt text.

## Bounded formatter requirement (hardened)

**Run the formatter/checker after every Write or Edit call, but do not loop.**

The tokenizer bugs affect the tokens the model emits. Formatters catch deterministic corruption; unbounded formatter/rewrite cycles create more corruption.

| File type             | Formatter | Command                       |
| --------------------- | --------- | ----------------------------- |
| Python                | ruff      | `uv run ruff format <file>`   |
| Markdown              | prettier  | `npx prettier --write <file>` |
| JavaScript/TypeScript | prettier  | `npx prettier --write <file>` |
| JSON/YAML             | prettier  | `npx prettier --write <file>` |
| Go                    | gofmt     | `gofmt -w <file>`             |
| Rust                  | rustfmt   | `rustfmt <file>`              |
| Shell                 | shfmt     | `shfmt -w <file>`             |
| SQL                   | sqlfluff  | `sqlfluff fix <file>`         |

## Rationalization patterns that WILL fail (Qwen-specific)

These are stronger versions of the generic ones in `FORMATTING.md`. Qwen agents are especially prone to them:

- ❌ "The indentation looks correct to me in the output" → the tokenizer can corrupt it silently on the next call.
- ❌ "I'll match the surrounding indentation by hand" → Qwen's tokenizer doesn't model indentation consistently. Manual matching drifts.
- ❌ "Let me re-read the file and check for whitespace" → you'll see the corruption and try to fix it manually, which will produce different corruption.
- ❌ "The formatter changed something I needed" → formatters are deterministic; the corruption was always there.
- ❌ "This is a one-character fix, no formatter needed" → one-character changes trigger the same tokenizer bugs.
- ❌ "I'll use a heredoc/echo to preserve exact whitespace" → heredocs route through the same tokenizer. Use `Write` then format.
- ❌ "Let me rewrite the file to fix the indentation" → rewriting preserves the same tokenizer-induced bugs. Use `Edit` + formatter.
- ❌ "The indentation is systematically wrong, I need to manually fix it" → run the formatter/checker once, make one minimal repair if needed, then stop on a second failure.

## Workflow

After every `Write` or `Edit`:

1. Run the formatter/checker for the file type exactly once.
2. If it fails, make one minimal `Edit` patch to the specific broken region.
3. Run the formatter/checker one more time.
4. If it still fails, stop and report the exact formatter/checker output.

Never loop on whole-file rewrites to fix indentation. For Python, include `python -m py_compile <file>` after formatting. For YAML, parse the file after formatting.

# Ollama homework models — thinking proxy

The homework models (`homework-reader`, `homework-robot-nvfp4`, `homework-robot-nvfp4-mlp`) are Qwen3.6-27B-uncensored-heretic-v2 variants with different quantizations. They all have the `thinking` capability in their GGUF metadata, which Ollama auto-enables by default.

## BUG-1011 (fixed): NVFP4 models produce empty responses without `think:false`

As observed at the time (Ollama 0.31.x), Ollama only responded to the native boolean parameter `think:false`, and none of Pi's `thinkingFormat` values produced it:

- Pi's `--thinking off` sends **nothing** (no parameter at all)
- `reasoning_effort: "none"` (string) — Ollama ignores
- `enable_thinking: false` — Ollama ignores
- `thinking: "none"` (string) — Ollama ignores

⚠ **The `reasoning_effort` line above is version-scoped and no longer holds on the OpenAI path.** As of Ollama 0.32.5, `reasoning_effort: "none"` on `/v1/chat/completions` suppresses thinking (INFO-1134). It is still ignored on `/api/chat` — the surface this BUG-1011 investigation was measuring — verified 2026-07-29 on `gemma4:coding-12b`, which emitted 510 chars of thinking with the field set. The list is kept as written because it was accurate for 0.31.x on the path it was testing; do not cite it as current behavior for the OpenAI-compatible endpoint.

**The fields are not interchangeable.** Each surface honors exactly one, and sending the wrong one fails silently rather than erroring: `reasoning_effort` on `/api/chat` does nothing, and `think:false` on `/v1/chat/completions` does nothing. That silence is what let the proxy's OpenAI-path suppression stay dead for three weeks.

NVFP4 quantization cannot follow `/no_think` when thinking is auto-enabled, producing empty responses. The Q4_K_M model (`homework-reader`) produces content alongside reasoning but still benefits from `think:false` for speed.

## Fix: thinking proxy on port 11435

`ollama-thinking-proxy` runs on port 11435 and forwards to Ollama on 11434, suppressing thinking server-side so a client that sends nothing still gets it disabled.

**Scope restored 2026-07-29 (INFO-1134).** It had been narrowed on 2026-07-07 (INFO-1089) because Ollama 0.31 ignored `think:false` on `/v1/chat/completions`, leaving the proxy's OpenAI-path injection a no-op. Ollama 0.32.5 honors `reasoning_effort: "none"` on that surface, and the proxy now injects it — so all three paths are covered again:

| Path                         | Injected                                             |
| ---------------------------- | ---------------------------------------------------- |
| `/api/chat`, `/api/generate` | top-level `think: false`                             |
| `/v1/chat/completions`       | `reasoning_effort: "none"` (+ a dead `think: false`) |
| `/v1/messages`               | `thinking: {"type":"disabled"}` + `think: false`     |

# Tool usage rules

## Bash tool ban — reading and writing file contents via Bash is FORBIDDEN

**Bash is for git, mkdir, rm, mv, curl, and navigation only — never for file content operations.** (Searching is the one narrow exception — see the closing note.)

### File content and web operations — zero exceptions for reads/writes

| Operation          | Allowed tool                                                   | Forbidden patterns                                                                                                                                                  |
| ------------------ | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Reading**        | `Read` (if editing) or `ctx_execute_file` (if analyzing)       | `cat`, `head`, `tail`, `sed -n \| cat -A`, `od -c`, `xxd`, `hexdump`, `strings`, or any other mechanism that outputs file content via Bash                          |
| **Writing**        | `Write` for new files or rewrites; `Edit` for targeted changes | `echo >`, `cat <<'EOF' >`, `printf >`, `tee`, `install`, `cp` (overwriting), `>` / `>>` redirection, heredocs, or any Bash mechanism that creates or modifies files |
| **Editing**        | `Edit` for targeted replacements                               | `sed -i`, `awk -i inplace`, `perl -pi` from Bash                                                                                                                    |
| **Searching**      | `Grep` or `Glob`                                               | `grep`, `rg`, `find -name`, `ag` from Bash (unless part of a pipeline without a dedicated tool equivalent)                                                          |
| **Web fetching**   | `ctx_fetch_and_index` → `ctx_search`                           | `WebFetch`, `Fetch` — these dump raw page bytes into context; use context-mode instead                                                                              |
| **Web extraction** | `ctx_execute` with `fetch()` inside the sandbox                | `WebFetch` + manual parsing — derive in the sandbox, only `console.log` output enters context                                                                       |

### Known rationalization patterns

- ❌ "Let me check for subtle whitespace issues" → still a file read. Use `Read` or `ctx_execute_file`.
- ❌ "Let me see the raw bytes / encoding" → still a file read. Use `Read` or `ctx_execute_file`.
- ❌ "This is just a small snippet / quick check" → still a file read.
- ❌ "I'll use `sed -n` to extract just a few lines" → still a file read. Use `Read` with `offset`/`limit`.
- ❌ "I'll use `cat -A` to show hidden characters" → still a file read. You don't need special tools; just `Read` the file.
- ❌ "I need to confirm the file exists first" → `ls` is fine, but piping it into `cat`/`head` is not.
- ❌ "I'll use a heredoc for exact whitespace control" → still a Bash file write. Use `Write` then run the formatter.
- ❌ "Let me use `cat`/`cat -v` to check the indentation" → still a Bash file read. Use `Read`.

### Web fetching rationalizations — ALL are violations

- ❌ "Let me use WebFetch to grab this page" → `ctx_fetch_and_index` — same network access, but raw bytes stay out of context
- ❌ "WebFetch is simpler for a quick lookup" → `ctx_fetch_and_index` — not simpler when it costs your entire reasoning budget
- ❌ "I need to see the full page" → `ctx_fetch_and_index` then `ctx_search` with broad queries
- ❌ "Let me try WebFetch first, and fall back if it fails" → Start with `ctx_fetch_and_index`. No fallback needed.
- ❌ "The page is small, so WebFetch is fine" → Context cost scales with output, not page size. Use `ctx_fetch_and_index`.
- ❌ "I need to extract specific data from a URL" → `ctx_fetch_and_index` → `ctx_search`, or `ctx_execute` with `fetch()` for extraction

**There is no task involving reading, writing, editing, or inspecting file contents for which Bash is the right tool. Searching is the one exception — `rg`, `grep`, `fd`, `find -name` are fine from Bash when the dedicated tool doesn't fit.**

## Renaming an Item

Renaming an item's file (changing its slug) breaks wikilinks and creates a stale OpenViking pointer. Avoid renaming when possible — pick a stable slug at intake. **Preferred path (TASK-1175; requires the app running AND `alwaysUpdateLinks: true` in `.obsidian/app.json` — committed, but verify links actually rewrote before trusting it)**: (a) run the step-1 `rg -l` sweep FIRST and keep the referrer list; (b) `obsidian vault=compendium rename path="<type-dir>/<old>.md" name=<new-stem>` — rewrites bare and piped wikilinks in referrers; (c) stage the rename **and every referrer from the captured list**: `git add "<type-dir>/<old>.md" "<type-dir>/<new>.md" <referrer files…>` — staging only the renamed pair leaves the rewritten referrers out of the commit; (d) re-run the step-1 rg and require zero hits on the old slug. When Obsidian is not running, use the manual procedure:

1. **Before renaming** — find all references to the current filename:

   ```bash
   rg -l "XXX-NNN-current-slug" bugs/ features/ ideas/ projects/ tasks/ errors/ info/ docs/
   ```

   (This `rg` sweep is a sanctioned **maintenance** operation — the `query.md` ban on lexical sweeps applies to item *discovery*, not to exhaustive reference-finding, where a lexical sweep is exactly the right tool.)

2. **Update wikilinks** — edit every `[[XXX-NNN-current-slug|...]]` reference to use the new slug. Verify by re-running the step-1 `rg` sweep (expect zero hits) — this works with the app closed; `obsidian vault=compendium backlinks path="<type-dir>/<old-filename>.md"` is an additional check only when the app is running.

3. **Rename the file** — use `git mv` to preserve history:

   ```bash
   cd ~/code/compendium && git mv "<type-dir>/XXX-NNN-old-slug.md" "<type-dir>/XXX-NNN-new-slug.md"
   ```

4. **Old OV pointer cleanup is handled by the manual sync** (BUG-1034) — do **not** queue a background sync. The `git mv` is detected as a rename by `sync --changed`, which deletes the stale pointer at the old URI and syncs the new path. After committing (and pushing), remind the user that an OV sync is pending: `~/code/homelab/main/compendium/cluster-sync.sh` (local fallback: `python3 _scripts/compendium-sync.py sync --changed`).

5. **Verify** — run the lint workflow's "Stale OV docs" check to confirm no ghost pointers remain.

6. **Commit** — include all changed files (wikilink updates + renamed file). The commit message is the rename record (no operations-log file):

   ```bash
   cd ~/code/compendium && git add <type-dir>/XXX-NNN-new-slug.md <all-updated-files> && git commit -m "XXX-NNN: rename slug (old-slug → new-slug)"
   ```

## ID Allocation

Each type has an independently monotonic counter. **Allocate by creating the item with `compendium-new`** — never by minting a number by hand:

```bash
compendium-new --type <type> --repo <repo> --title "..."
```

To ask what the next ID *would* be without allocating it:

```bash
_scripts/next-id.sh <PREFIX> [--scope work|personal]
```

Where `<PREFIX>` is one of `BUG`, `FEAT`, `GUIDE`, `IDEA`, `IMPR`, `INFO`, `PROJ`, `TASK`, or `ERR`. The script recursively scans the active type directory (including partitioned subdirs like `bugs/{mage,dipdash,other,homelab}/`), the `archive/{type}/` tree, and the legacy `tasks/PROJ-NNN/` groups so archived and project-grouped items are covered. It also scans every linked worktree and the remote's branch heads (all of `origin` up to a ref cap — machine branches `pop`/`workbook` included; cap-fallback hardening tracked in [[TASK-1153-other-verify-and-harden-id-slug-collision-detection-across-machine|TASK-1153]]), so a sibling session's uncommitted intake and a pushed-but-unpulled intake on any branch both count.

### Why allocation must go through `compendium-new`

The collision guarantee has two halves, and the scan alone is not enough:

| Half                         | Lives in                          | Provides                         |
| ---------------------------- | --------------------------------- | -------------------------------- |
| Cross-worktree + remote scan | `_scripts/next-id.sh` (this repo) | Sees every existing ID           |
| Intake lock                  | `compendium-new` (dotfiles repo)  | Serializes the scan→write window |

`next-id.sh` reads and exits. Between one caller reading `BUG-1051` and writing that file, a second caller can read `BUG-1051` too — a TOCTOU race the scan cannot close. `compendium-new` takes a lock under the repo's **shared Git common dir** (not `$VAULT`, since every worktree has its own) so sibling worktrees serialize. Regression guard: `CrossWorktreeAllocation` in `_scripts/test-compendium-new.py`.

Treat a bare `next-id.sh` call as advisory only.

| Type        | Prefix      | Active dir                             | Backlog dir         | Terminal dir                                          |
| ----------- | ----------- | -------------------------------------- | ------------------- | ----------------------------------------------------- |
| Bug         | `BUG-NNN`   | `bugs/{domain}/`                       | `bugs/backlog/`     | `bugs/{domain}/resolved/` or `archive/bugs/{domain}/` |
| Feature     | `FEAT-NNN`  | `features/{domain}/`                   | `features/backlog/` | `features/completed/` or `archive/features/`          |

| Project     | `PROJ-NNN`  | `projects/`                            | `projects/backlog/` | `projects/completed/` or `archive/projects/`          |
| Task        | `TASK-NNN`  | `tasks/{domain}/` or `tasks/PROJ-NNN/` | `tasks/backlog/`    | `tasks/completed/` or `archive/tasks/`                |

## YAML Safety Rules

These rules prevent the most common frontmatter corruption patterns found in the compendium vault. Violations break Obsidian's YAML parser, making all frontmatter fields invisible to Dataview queries and the Properties panel.

### 1. Wikilinks in YAML lists must be double-quoted and on separate lines

Every `[[...]]` wikilink in a YAML list (e.g., `related:`, `sources:`) must be double-quoted and each item on its own line:

```yaml
# Correct
related:
  - "[[BUG-042-mage-some-issue|BUG-042 Some issue]]"
  - "[[FEAT-016-dipdash-feature|FEAT-016 Feature]]"

# Wrong — unquoted wikilinks parse as nested flow sequences, not strings
related:
  - [[BUG-042-mage-some-issue|BUG-042 Some issue]]

# Wrong — multiple items concatenated on one line causes cascade corruption
related:
  - "[[BUG-042|BUG-042]]"  - "[[FEAT-016|FEAT-016]]"
```text

### 2. No double quotes inside wikilink display text

Double quotes inside `[[...]]` break YAML parsing because the outer double quotes close at the first inner `"`. Replace inner double quotes with single quotes:

```yaml
# Correct
related:
  - "[[TASK-135|Add 'recommended tools' section to README]]"

# Wrong — inner " closes the outer double-quote, orphaning the rest
related:
  - "[[TASK-135|Add "recommended tools" section to README]]"
```text

### 3. Never double-quote `retrieval_summary`

`retrieval_summary` must be a **single-line YAML plain scalar, 200 characters or fewer**. Never double-quote it or use `>-` folded block scalars. If the value contains `: ` (colon-space), use single quotes.

```yaml
# Correct — plain scalar
retrieval_summary: Cross-env pipeline import causes FIVETRAN_DB error from hardcoded prod database names.

# Correct — single quotes for colon-space values
retrieval_summary: 'Race condition in same-customer lookup: concurrent requests hit stale cache'

# Wrong — double-quoted (inner quotes or continuation lines break parsing)
retrieval_summary: "Long description that wraps across lines and breaks YAML..."

# Wrong — folded block scalar
retrieval_summary: >-
  Long description that spans
  multiple lines.
```text

### 4. No duplicate YAML keys

Every YAML key must appear exactly once in a frontmatter block. The most common duplicates are `repos:` and `ov_mode:` — both are emitted at the top and again at the bottom by some agents. Only the first occurrence is parsed; subsequent duplicates are silently ignored by some parsers but cause errors in others.

```yaml
# Correct — each key appears once
repos: [mage]
ov_mode: pointer

# Wrong — duplicate keys
repos: [mage]
ov_mode: pointer
repos: [mage]    # duplicate — remove
```text

### 5. `>-` folded block scalars are only for `status_detail` starting with digits

The `>-` folded block scalar is a valid YAML construct but must only be used for `status_detail` values that start with a digit (to avoid YAML's numbered-list interpretation). Never use `>-` for `retrieval_summary` or any other field that should be a single-line value.

See the "YAML Gotcha" section in `projects.md` and `CLAUDE.md` for the `status_detail` pattern.
````

The narrow reading was corrected rather than enforced (PR #115 review): migrating ~1,556 values to fabricate `_sources/` paths that were never archived would destroy real provenance to satisfy a contract the vault outgrew.

| Code / config path | `common.pipeline_path`                                    |
| Direct observation | `'Measured on pop, Ollama 0.32.4, 2026-07-27'`            |

Prefer an archived `_sources/` file when raw material exists and is worth keeping — it is the only shape that survives the original going away. Otherwise record the most specific pointer available. ## Project ↔ Task Relationship

Tasks always belong to a project, and the link is bidirectional. When creating tasks under a project:

1. **Project is created first.** A task cannot exist without a parent `PROJ-NNN`.
2. **Each task carries `project: PROJ-NNN`** in its frontmatter (required field, see `.claude/instructions/tasks.md`).
3. **The project's `# Task List` section lists every task** as a piped wikilink with a checkbox:

```text

## YAML Gotcha — `status_detail` Values Starting With Digits

If a `status_detail` value begins with a digit (e.g., "8 of 10 questions"), the YAML parser will interpret it as a **numbered list** and break Obsidian frontmatter rendering. Use a **folded block scalar** to disambiguate:

```yaml
status_detail: >-
8 of 10 design questions decided. 2 remain open for Joel:
  triggering mechanism (deploy-gate vs on-demand),
  pipeline automation (full fleet vs smoke suite).
```text

Alternative (simpler) fix: add a leading space inside the quotes:

```yaml
status_detail: " 8 of 10 design questions decided..."
```text

The folded block scalar (`>-`) is preferred — it produces a single logical line in the parsed output while avoiding the numeric-list ambiguity.

# Guides — Frontmatter, Body, and Lifecycle

Guides are numbered procedural documents (`GUIDE-NNN`) that capture **how to do it** — step-by-step playbooks, operational runbooks, and task procedures. They are distinct from INFO entries (which capture **what we know** — Q&A, reference data, discovered facts).

## When to use GUIDE vs INFO

| Use GUIDE when...                               | Use INFO when...                                  |
| ----------------------------------------------- | ------------------------------------------------- |
| The content is a procedure (do this, then this) | The content is a fact (X is Y)                    |
| It has numbered steps or a workflow             | It's a Q&A, reference table, or data lookup       |
| It includes commands, SQL, or code to run       | It describes architecture, data flow, or a system |
| It would help someone repeat the task           | It would help someone understand a system         |
| It has a "Prerequisites" section                | It has a "Context" or "Background" section        |

When in doubt, prefer GUIDE for anything with steps.

## Frontmatter

````yaml
---
title: "Short Descriptive Title"
type: guide
topic: kebab-topic                    # e.g., bulk-data-upload, pipeline-debugging
repos: []                             # repos involved, e.g., [mage, dipdash]
people: []                            # people involved or who requested
customers: []                         # customer names, e.g., [conagra, vestis]
themes: []                            # broad themes, e.g., [snowflake, fixed-width-parsing]
domains: []                           # knowledge domains, e.g., [data-pipeline, snowflake]
tags: []                              # search-friendly tags
aliases: []                           # alternative names for search
retrieval_summary: null              # Single-line plain scalar, ≤200 chars. Never double-quote or use >-. See vault-structure.md YAML Safety Rules.
source_of_truth: this document | <url>  # where the canonical version lives
date_created: YYYY-MM-DD
date_updated: YYYY-MM-DD
last_validated: YYYY-MM-DD           # last time the procedure was tested end-to-end
related: []                           # wikilinks to related items
ov_mode: pointer
---
```text

### Key fields

- **`last_validated`**: When the guide was last tested end-to-end. Bump this when you successfully run the procedure. If the guide is stale (last_validated > 6 months ago), flag it for re-validation.
- **`source_of_truth`**: `this document` if the compendium is canonical, or a URL if an external doc is canonical and this is a local copy.
- **`topic`**: A kebab-case topic that groups related guides (used for directory partitioning).

## Body structure

Every guide should follow this outline:

```markdown
# Guide Title

One-sentence summary of what this guide covers and when to use it.

---

# Prerequisites

What you need before starting: tools, access, env vars, files, permissions.
Link to other guides or INFO entries for context.

# Overview

High-level flow of the procedure. One paragraph or a simple diagram.

# Steps

## Step 1: Step Title

What to do and why. Include exact commands, SQL, or code snippets.

**Gotchas:**
- Common mistake X and how to avoid it

## Step 2: ...

# Performance Reference

Benchmarks, timing data, or sizing estimates from actual runs.

# Verification

How to confirm the procedure succeeded. Include exact commands or queries.

# Related

- Cross-links to related guides, INFO entries, or external docs
````

Sections can be omitted if they don't apply (e.g., a simple guide may not need Performance Reference). Never omit Prerequisites, Overview, or See Also.

### Style rules

- **Language on every code fence** — always write ` ```bash `, ` ```yaml `, ` ```text `, etc. Never write a bare ` ``` ` fence (MD040 lint error).
- **Exact commands** — include full commands readers can copy-paste, not paraphrased descriptions.
- **Cross-link** — link to prerequisite guides, related INFO entries, and external docs.

## Lifecycle

Guides are **append-only** — no status transitions, no terminal state. Like INFO and ERR entries:

- No `status` field in frontmatter
- No `date_completed` field
- No moves to resolved/completed directories
- Update `date_updated` and `last_validated` when the guide is revised or re-tested
- Guides live in `guides/` with domain subdirectories (like `info/`). All entries must be in a subdirectory — never at the `guides/` root.

| `ov_mode`           | yes      | string       | Always `pointer`                                                                                                     |

- `root_cause` → `# Root Cause` body section
- `fix_summary` → `# Fix Guidance` body section
- `resolutions` → removed (resolution is now in the body)
- `signatures` on ERR-RES → merged into ERR `signatures` list

## Status Lifecycle

Error signatures have a simple two-state lifecycle:

- **`active`** — Error pattern known, no fix documented yet (the 17 unresolved ERR entries)
- **`resolved`** — Error pattern known, fix guidance documented (the 38 merged entries)

| Section          | Required        | Purpose                                                                             |

| `# Context`      | always          | Pipeline stage, data scenario, config that produces this error.                     |
| `# Root Cause`   | when `resolved` | Detailed explanation with file:line references, data flow, chain of events.         |
| `# Fix Guidance` | when `resolved` | Step-by-step fix instructions with code snippets.                                   |
| `# Bugs`         | optional        | Links to incident bugs.                                                             |
| `# Related`      | optional        | Cross-links to bugs, PRs, commits, related entries.                                 |

---

## Agent Discovery Workflow

When an agent encounters an error message:

1. **Substring match**: Scan `signatures` frontmatter fields in `errors/ERR-*.md` for matching text fragments.
2. **Match found?** Read the matched `ERR-NNN` file. If `status: resolved`, the `# Root Cause` and `# Fix Guidance` sections contain the fix. Present findings.
3. **No match?** Flag as a potentially novel error pattern. Do not file automatically.

To check signatures efficiently, extract the YAML `signatures:` list from each `errors/ERR-*.md` file and test each entry as a substring (`match_mode: substring`) or regex (`match_mode: regex`) against the error text.

---

## Location

Place error entries under `errors/{domain}/`, where `{domain}` is the system that emits the error:

- `errors/mage/` — Mage pipeline errors (including Snowflake, dbt, pipeline-path, type conversion, identifier errors)
- `errors/dipdash/` — DIPDash errors
- `errors/homelab/` — homelab / Kubernetes / networking / OpenViking / Hermes errors
- `errors/robots/` — robotics / MLX / ComfyUI errors
- `errors/system/` — system-level errors (hardware, display, OS)
- **No matching subdir?** Create one. If the error is scoped to a new domain, create `errors/{domain}/` and place the file there. Do not leave entries at the `errors/` root.

---

### Filing a new error pattern

1. Extract distinctive text fragments from the error message as signatures.
2. File `ERR-NNN` with `status: active` and the `# Pattern` and `# Context` sections.
3. If a BUG was filed during the incident, link it in `bugs:` and `# Related`.
4. When the root cause and fix are identified, update the ERR entry: add `# Root Cause` and `# Fix Guidance` body sections, and set `status: resolved`.

## Query workflow

Use this when the user asks "has this been fixed before?", "do we have a bug
for X?", "any open bugs touching \<system\>?", "what features are proposed?",
"show me all ideas", or similar recall questions.

1. **Search OpenViking first.** Prefer `viking_find(target_uri:
"viking://resources/compendium/")` over `viking_search` for compendium
   discovery — it takes an unambiguous `target_uri` instead of a `scope`. Reserve
   `viking_search` for cross-namespace queries, and when you do use it,
   `scope: "resources"` is the only valid value for compendium content (not
   `"Compendium"` — that 400s).
2. **Score the hits** before accepting any of them:

   | Score       | Treatment                                                             |
   | ----------- | --------------------------------------------------------------------- |
   | `>= 0.65`   | Likely relevant if title/abstract matches intent. Accept.             |
   | `0.50–0.65` | Possible — run `rg` to confirm unless title/abstract is an exact fit. |
   | `< 0.50`    | Weak by default — run `rg`; if that's also weak, report no match.     |

3. **Fall back to `rg`** as a low-token lexical verifier, not the answer source.
   Search compact term alternations across item directories, prefer hits in
   frontmatter search fields, and read only the top 1-3 candidate files.
4. **Verify and read.** Extract the `Path: ~/code/compendium/...` pointer from
   any OV hit and read the local markdown file for the actual answer — OV is a
   discovery layer, not the source of truth.
5. **Synthesize.** Note status; if resolved/completed, surface the fix; if
   active, surface the open-question state. If both OV and `rg` come back weak
   or unrelated, say the compendium has no strong match — don't force a
   connection.

## Critical shared conventions

### ID allocation

Each type has its own monotonic namespace (`BUG-NNN`, `FEAT-NNN`, `IDEA-NNN`,
`IMPR-NNN`, `PROJ-NNN`, `TASK-NNN`) — never collide across active and completed
within a type. Allocate the next ID by scanning all relevant directories, e.g.
for bugs:

```bash
find ~/code/compendium/bugs -maxdepth 2 -name 'BUG-*.md' | \
  grep -oE 'BUG-[0-9]{3}' | sort -u | tail -1
```

Swap the prefix and directory list for other types (see
`~/code/compendium/CLAUDE.md` for the per-type directory sets, which include
`backlog/` and `completed/`/`resolved/` subdirs). Next ID = highest + 1,
zero-padded to 3 digits. Deleting an item leaves a hole — never renumber to
fill it; external references (OV, commits, PRs) would break.

### Status → location invariant

| Type         | Active                           | Backlog                 | Terminal                                         |
| ------------ | -------------------------------- | ----------------------- | ------------------------------------------------ |
| Bugs         | `bugs/` (domain subdirs)         | `bugs/backlog/`         | `bugs/resolved/` — `fixed`, `wontfix`            |
| Features     | `features/`                      | `features/backlog/`     | `features/completed/` — `shipped`, `dropped`     |
| Ideas        | `ideas/`                         | `ideas/backlog/`        | `ideas/completed/` — `shipped`, `dropped`        |
| Improvements | `improvements/` (domain subdirs) | `improvements/backlog/` | `improvements/completed/` — `shipped`, `dropped` |
| Projects     | `projects/`                      | `projects/backlog/`     | `projects/completed/` — `completed`, `cancelled` |
| Tasks        | `tasks/`                         | `tasks/backlog/`        | `tasks/completed/` — `done`, `cancelled`         |

Complete and reopen are the only operations that cross directory boundaries —
always via `git mv` so history follows the file.

### Filename convention

`XXX-NNN-{repo}-kebab-slug.md`. `{repo}` matches the `repo:` frontmatter field
(`other` when null). The slug describes the symptom (bugs), feature/idea, or
work item — pick one and keep it stable; renaming breaks wikilink resolution
unless every `[[XXX-NNN ...]]` reference is updated at the same time.

### OpenViking namespaces

- `viking://resources/compendium/bugs/resolved/`
- `viking://resources/compendium/features/completed/`
- `viking://resources/compendium/ideas/completed/`
- `viking://resources/compendium/improvements/completed/`
- `viking://resources/compendium/projects/completed/`
- `viking://resources/compendium/tasks/completed/`
- `viking://resources/compendium/` — reconciliation history, vault-level metadata

Active items get lightweight pointer payloads (ID, title, status, path) for
discovery/dedup, pushed only by a **manual** sync. Terminal items get richer
distilled resolution records (root cause, fix, verification, gotchas) pushed
to the matching `completed/`/`resolved/` namespace. Neither push happens
automatically — intake/status/reopen workflows commit the vault change and
leave a pending-sync reminder.

## What not to do

- Don't modify `~/code/BUGS.md` — archived, pre-vault, read-only.
- Don't queue automatic OV syncs — commit and push, then remind the user the
  manual sync is pending.
- Don't silently pick a workflow when intent is ambiguous — ask.
- Don't re-use or renumber IDs — deleted IDs stay deleted.
- Don't omit the manual-sync reminder for newly created/changed active items.

# Compendium Compaction

Shorten verbose entries in `~/code/compendium/` — collapse dated investigation
logs into a `## History` section, merge overlapping sections, condense duplicated
prose — without changing what the entry **asserts**. Every decision, ID, date,
wikilink, and completion field must survive verbatim.

This is a script sandwich. Do not skip either script:

```text
_scripts/compaction-assess.py   ->   agent compacts prose   ->   _scripts/compaction-validate.py
   (which entries?)                    (judgment)                   (did anything protected move?)
```

## Levels

Additive — each includes the one above. **Automated/unattended passes are always
Conservative.** Moderate and Aggressive require the user to name them explicitly.

| Level        | Adds                                                                         |
| ------------ | ---------------------------------------------------------------------------- |
| Conservative | Remove clear duplication, merge sequential updates, condense verbose prose   |
| Moderate     | + Replace verbatim logs with signature summaries, collapse prose to bullets  |
| Aggressive   | + Restructure to reference format, drop investigation notes with no decision |

Aggressive is the only level that may remove a top-level `#` section, and only
for cancelled/dropped items — requires
`--allow-section-removal '<exact heading>'` on the validator (repeatable, covers
only the named headings), passed only after the user approves each specific
removal.

## Never compact

- Frontmatter — not one byte. It's the retrieval contract and the OV index key.
- Completion/status fields — `status`, `fixed_in`, `completed_in`, `resolution`.
- Decision outcomes — compact the deliberation, keep the verdict.
- Error signatures, SQL, commands, IDs, filenames, dates, URLs, wikilink targets.
- Top-level `#` section headers (the type's body contract from `_templates/`).
- Checked acceptance criteria (`- [x]`) — dropping one erases a completion signal.
- Guides/info entries' fenced blocks — for reference types the commands are the
  content.

Safe to remove: duplicate reasoning, dead-end exploration, verbose setup
narration, verbatim resolved logs (Moderate), empty template sections, status
churn ("moved to in-progress", "moved back to todo").

## Steps

1. **Assess** — never eyeball the vault for candidates.

   ```bash
   cd ~/code/compendium
   uv run python _scripts/compaction-assess.py --top 15
   uv run python _scripts/compaction-assess.py --base origin/main --type bug,task   # PR-scoped
   ```

   Each candidate prints its signals (`chronological(9 dated headings)`,
   `log-bulk(200 fenced lines)`, `empty-sections(3)`) — they map onto the
   patterns below and tell you what to do, not just where. Entries touched in
   the last 48 hours are withheld (`--include-recent` to see them) — ask before
   compacting one.

2. **Work on a branch** — never compact on `main`. A multi-entry pass belongs in
   a worktree; see `~/code/compendium/CLAUDE.md` § Worktree & Branch Conventions.

3. **Compact, one entry at a time.** Read the whole entry first. Apply the
   pattern(s) the assessor's signals pointed at, at the level in force
   (Conservative unless asked). Leave the frontmatter untouched; don't update
   `date_updated` — a compaction is not new information.

   | Pattern                    | Transformation                                                                                   |
   | -------------------------- | ------------------------------------------------------------------------------------------------ |
   | Chronological Collapse     | Several dated investigation sections -> one `## History` with one bullet per date                |
   | Table Deduplication        | Same data in prose and a table -> keep the table                                                 |
   | Section Merge              | "Proposed Fix" + "Prior Fix Attempts" + "Investigation Notes" -> one Fix + History               |
   | Cross-Reference Compaction | Content already covered by a linked entry -> a one-line wikilink to it                           |
   | Hub Entry Compaction       | "Representative Bugs" tables -> a "Covered by" wikilink list                                     |
   | Superseded Option Removal  | Several evaluated options where one was chosen -> the chosen one + a one-line note on what lost  |
   | Cancelled-Item Compaction  | Aggressive only: drop Approach/Tasks/Acceptance for a cancelled feature, keep the reason it died |

4. **Format, then validate — in that order.** `prettier` rewrites quote style in
   the frontmatter block, so validating first and formatting after leaves the
   committed file in a state the validator would then reject.

   ```bash
   npx prettier --write <path>
   uv run python _scripts/compaction-validate.py <path>            # vs the committed version
   uv run python _scripts/compaction-validate.py --base origin/main <path>
   ```

   Validation is blocking — every check passes before the entry is staged. The
   validator compares sets, not lines (wikilink targets, item IDs, dates, URLs)
   and compares frontmatter per parsed key, not by bytes. If it fails, fix the
   entry — never relax the check. Two escape hatches, both user-approval-gated
   per use: `--allow-section-removal '<exact heading>'` and
   `--allow-fence-changes` (Moderate log replacement or repairing a structurally
   broken fence). Checked (`- [x]`) items compare by identity, not count.

5. **Show the diff, then let the human confirm.** Present `git diff` for the
   entry and name your two or three riskiest judgment calls. This gate is not
   optional. Then commit with a `compact:` prefix naming the entries, and push.

## Parallel passes (multi-entry)

Entries are disjoint files — fan out one subagent lane per entry for steps 3-4;
everything else stays in the parent (assess/candidate selection, worktree setup,
the consolidated human gate, all git operations, and the escape-hatch flags,
which a lane must never pass). Lanes are always Conservative regardless of the
level named for the pass; on validation failure a lane fixes and re-validates,
except section-removal violations, which it reports verbatim and leaves for the
parent to raise at the gate. Stay serial for one or two entries, or for entries
that cross-reference each other heavily.

## Common mistakes

- Compacting the frontmatter's `retrieval_summary` because it reads verbosely —
  it's frontmatter, always out of scope.
- Collapsing three dated sections that reached three different conclusions —
  keep the disagreement, it's the content.
- Dropping a "redundant" link line — the link target is never redundant. Run
  the validator and believe it.
- Compacting an entry updated yesterday — ask first.
- Going Moderate just because the entry is long — length is not consent.

# Compendium Complete

Mark an item in `~/code/compendium/` fixed, shipped, dropped, done, or cancelled. Covers frontmatter updates, the file move into a terminal directory, ERR/INFO linkage checks, `index.md` updates, and committing.

**Always read `~/code/compendium/CLAUDE.md` first** — it maps each task to the relevant sub-file. Load `.claude/instructions/workflows/completion.md` for the step-by-step workflow and the type-specific file (`.claude/instructions/bugs.md`, `.claude/instructions/features.md`, etc.) for terminal statuses and completion fields. Do not inline the schema from memory — those files are the source of truth.

If multiple items across different types are being completed together, batch the commits: one message per type group.

## Steps

1. **Identify the item**

   Determine: type prefix (`BUG`→bug, `FEAT`→feature, etc.), current status, the type's completion field (bugs → `fixed_in`, everything else → `completed_in`), the terminal status being applied, and the target directory. Look these up in CLAUDE.md's type-specific details table.

2. **Run ERR/INFO linkage checks — BEFORE any file move**

   ```bash
   cd ~/code/compendium && uv run python _scripts/check-linked-entries.py <ID> <path/to/item.md>
   ```

   Surfaces: linkage gaps (ERR entries that reference the item but don't list it in `bugs:`), unresolved ERR signatures (`status: resolved` but missing `## Root Cause`/`## Fix Guidance`), and candidate new INFO/ERR entries. Exit code is always 0 — advisory only. Report findings; do not block on them. Note any gaps in the item's body (e.g. its verification section).

3. **Update the frontmatter**

   Use `Read` + `Edit` — never `sed`. Set:

   - Terminal `status` (e.g. `fixed`, `shipped`, `completed`)
   - Completion field (`fixed_in` for bugs; `completed_in` otherwise) — commit hash, PR number, or descriptive string
   - `date_updated` → today
   - Remove `session:` if present (item is no longer active work)
   - Refresh retrieval metadata if present (`people`, `customers`, `themes`, `domains`, `aliases`, `tags`, `retrieval_summary`)
   - **Colon rule**: if `retrieval_summary` contains `": "`, single-quote the whole value (`retrieval_summary: 'Foo: bar'`) — unquoted, `lint-frontmatter.py` fails the commit.
   - Fill the verification section (`## Verification` for bugs, `## Completion` for features, etc.)

   Optional scaffold: `_scripts/complete-item.py <ID> --status <terminal> --ref <ref>` sets frontmatter and does the `git mv` (step 5) — dry-run by default, add `--apply` to write. It never touches `index.md` (step 7 stays hand-edited).

4. **Re-run the linkage check**

   After frontmatter changes, re-run step 2's check — updated `bugs:`/`related:` fields can change the findings. Compare against the first pass and report deltas.

5. **Move the file with `git mv`**

   ```bash
   cd ~/code/compendium && git mv "bugs/<filename>.md" "bugs/resolved/<filename>.md"
   ```

   | Type        | Target directory          | Terminal statuses    |
   | ----------- | ------------------------- | -------------------- |
   | bug         | `bugs/resolved/`          | fixed, wontfix       |
   | feature     | `features/completed/`     | shipped, dropped     |
   | idea        | `ideas/completed/`        | shipped, dropped     |
   | improvement | `improvements/completed/` | shipped, dropped     |
   | project     | `projects/completed/`     | completed, cancelled |
   | task        | `tasks/completed/`        | done, cancelled      |

   Mirror domain subdirectories where they exist: `bugs/<repo>/BUG-*.md` → `bugs/resolved/<repo>/`; `improvements/<repo>/IMPR-*.md` → `improvements/completed/<repo>/`. Tasks nest under their parent project: `tasks/TASK-*.md` → `tasks/completed/<PROJ-NNN>/TASK-*.md` (create the dir if needed).

6. **Do NOT push to OpenViking — describe the pending manual sync instead**

   This workflow never mutates OV. Record enough detail in the vault for the user's later manual sync to do both of:

   - **Distilled record** in the matching namespace (`viking://resources/compendium/bugs/resolved/`, `.../features/completed/`, `.../ideas/completed/`, `.../improvements/completed/`, `.../projects/completed/`, `.../tasks/completed/`) — ID + title, symptom/description, root cause or approach (1-2 paragraphs), resolution applied (commit/PR/config change), verification notes, gotchas.
   - **Pointer cleanup** — the old active-path pointer, including cross-references, needs updating/removing once the file moved.

   **OV sync is manual (BUG-1034) — do not run `compendium-sync.py` in the background from this workflow.** The `git mv` is what makes the rename detectable; the user's next manual `--changed` sync (canonical: `~/code/homelab/main/compendium/cluster-sync.sh`; local fallback: `python3 _scripts/compendium-sync.py sync --changed`) picks it up after commit + push. If OV is unavailable, note in the item body (one line) that the OV push is pending.

7. **Update `index.md`**

   Remove the entry from the active section; add it to the type's `## Completed` / `## Resolved` section (newest on top). Format: `- [[XXX-NNN-slug|Title]] — <one-line summary>`, matching the existing section's style.

8. **Commit**

   ```bash
   cd ~/code/compendium && git add <type-dir>/<completed-dir>/XXX-NNN-*.md index.md
   git commit -m "<type>: complete XXX-NNN — <short description>"
   ```

   Batch across types in one message when completing several items at once:

   ```bash
   git commit -m "bugs: complete BUG-094 and BUG-102; features: ship FEAT-003"
   ```

## Conventions

- IDs are monotonic per type — never renumber or reuse.
- Filename must match frontmatter type + ID; moving preserves the filename.
- Only complete/reopen cross directory boundaries — every other status transition stays in place (`/compendium-status`).
- OV is advisory for the linkage check — if unavailable, proceed with local-file steps and note the missing push.

## Rules — do not skip

- **Never omit the manual-sync reminder** — until the user runs it, OV may keep the stale active pointer and lack the terminal distilled record.
- **Never skip the linkage check** because it's advisory — always report findings, both passes.
- **Never move files without `git mv`** — history must follow the file.
- **Never commit before updating `index.md`** — it's part of the same logical change.
- **Never auto-push to OpenViking from this workflow** — that is always a separate, user-run manual step.
