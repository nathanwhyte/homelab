# Ollama serving lessons — pre-flight for the timmy (RX 9070 XT / Vulkan) campaign

Consolidated 2026-08-28 from a four-lane sweep of the compendium vault (`info/`, `guides/`, `bugs/`, `errors/`, `improvements/`, `ideas/`, `tasks/`), `~/.claude/GUARDRAILS.md` + `QWEN.md`, the dotfiles Modelfiles and `ollama-serve` scripts, and this repo's benchmark reports, tools and manifests. Purpose: everything learned benchmarking on pop and timmy since May, so the IDEA-1090 campaign (FIM + agent-partner cohabitation, retry sweep on 0.33.x) does not re-learn it.

**Read the scope column.** Most of the pop findings were measured on the **MLX** engine. Timmy runs **llama.cpp/GGUF on Vulkan**, so:

## 2. Slots, parallelism and residency (scheduler)

| #   | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Scope          | Evidence                                                                          |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | --------------------------------------------------------------------------------- |
| S1  | `OLLAMA_NUM_PARALLEL` is a request, not a grant. The runner picks `n_seq_max` **per model**: gemma4:12b got 8 slots, `qwen3.5:9b` and `nemotron-3-nano:4b` got **1** with 15.9 GiB free — not a VRAM fit issue, cause undiagnosed, measured on 0.31.1 and never re-checked. A one-slot runner cannot batch; every "this model doesn't scale" row from 2026-08-14 was retroactively invalidated. Verify per model from the runner log (`n_seq_max`, `new slot, n_ctx`); `run-vulkan-benchmark-jobs.sh capture_backend_proof` now keeps those lines. | timmy / gguf   | INFO-1106:117; slot-probe-20260814 README; comparison matrix:53-59; TASK-1013:152 |
| S2  | llama.cpp reserves KV **eagerly** at load, sized `num_ctx × NUM_PARALLEL`; the loaded runner is keyed by `(model, num_ctx, num_parallel, …)` so a different context size forces a reload. MLX allocates lazily (~0.11 GiB per 1k tokens, monotonic until `ollama stop`).                                                                                                                                                                                                                                                                           | gguf vs mlx    | INFO-1106:77,87; INFO-1054:47-66; INFO-1145:118-143                               |
| S3  | `MAX_LOADED_MODELS=1` + `KEEP_ALIVE=-1` means **last model wins forever**, not "preferred model stays resident": any other load (an embed call, a probe) evicts the resident runner and its prefix cache. A request-level `keep_alive` can override the server lifetime downward. Eviction is async — a load issued right after evicting can still see the old allocation; capture `gpu memory … free=` lines per load.                                                                                                                            | server / timmy | INFO-1106:87,108; slot-probe README "co-residency confound"                       |
| S4  | On the 9070 XT, `NUM_PARALLEL` 1→2 gave +43 % aggregate at c=2 for −11 % per-slot; distinct concurrent prefixes need one slot each or they thrash (86 vs 173 tok/s aggregate at 6 prefixes). | S5  | Live vs benchmark posture: production is `NUM_PARALLEL=2` (one pinned runner); matrix runs patch to 8 and **must restore** afterwards. Restoring rolls the pod and destroys the container log — capture backend proof and slot lines before restoring.                                                                                                                                                                                                                                                                                             | timmy          | ollama-deployment.yaml NUM_PARALLEL comment; comparison matrix "superseded gates" |
| S6  | MLX serializes same-model concurrency (TTFT stacks, aggregate flat, `NUM_PARALLEL` inert); GGUF batches (322→388 tok/s aggregate 2→4 clients). | S7  | Two resident models = two runner processes, no cross-model queueing; on discrete VRAM they contend for compute/bandwidth only (FIM −28 % decode worst case under chat, TTFT ≤0.43 s). | S8  | One local-model consumer at a time, session-wide, counted by what the work drives. | S9  | Prefill wedge: llama.cpp/MLX prefill can stall indefinitely near end-of-context after a client disconnect (semaphore leak); `NUM_PARALLEL` does not help once wedged. | S10 | `OLLAMA_LOAD_TIMEOUT`: default 5 m is too tight for timmy's PVC/ROCm cold starts and too loose for pop — pop 2 m, timmy 15 m.                                                                                                                                                                                                                                                                                                                                                                                                                      | both           | BUG-1027:47-68                                                                    |

**S11 — post-restart warm-up holds a slot (found 2026-08-28, `timmy`).** The deployment's warm hook ran `ollama run deepseek-coder-v2:fim "// warmup"` — a real generation on the base FIM tag, which has no chat template and no natural stop — and held runner slot 1 for **2m39s** after the 0.33.1 restart, serialising every concurrent request through slot 0 (FIM TTFT 3.19 s p50 with one background stream, vs 0.26 s once it finished). Fix drafted in `llama/ollama-configmap.yaml`: load-only `/api/generate` POST with an empty prompt over bash `/dev/tcp` (image has no curl), verified to return `done_reason: "load"` immediately. Until applied: never benchmark within ~3 min of an ollama pod restart, and check `kubectl logs … | grep '127.0.0.1 | POST "/api/generate"'` shows the warm request completed. Evidence: `benchmarks/results/fim-contention-20260828-v0.33.1/README.md`.

**S12 — the per-model `n_seq_max = 1` cap is an Ollama scheduler blocklist (found 2026-08-28, `server`).** `server/sched.go` forces `numParallel = 1` for the families `mllama, qwen3vl, qwen3vlmoe, qwen35, qwen35moe, qwen3next, lfm2, lfm2moe, nemotron_h, nemotron_h_moe, nemotron_h_omni` before the runner launches — logged as `model architecture does not currently support parallel requests architecture=<family>` (present in timmy's pod log for `qwen35`). It guards a llama.cpp hybrid-attention crash fixed upstream 2026-03-08 (ggml-org/llama.cpp#20222 → #20232); ollama/ollama#17144 unblocks `qwen35`/`qwen35moe`, is validated on Vulkan/CUDA/ROCm, and is unmerged as of 2026-08-26. No env var or Modelfile knob bypasses it; it is independent of backend, quant, context and VRAM. This closes S1's "cause undiagnosed": qwen3.5:9b and nemotron-3-nano get one slot by list membership, gemma4 gets what `NUM_PARALLEL` asks for. Grep the log line, not `ollama ps`, to know which case a model is in. Evidence: `benchmarks/results/pair-cohab-20260828/README.md` §1.

**S13 — a request without `num_ctx` to a tag with none baked reloads the runner at `OLLAMA_CONTEXT_LENGTH` (found 2026-08-28, `server`).** The loaded runner is keyed by `num_ctx` (S2); the cohabitation run's partner requests omitted it and each partner was silently reloaded at 131072 on its first call — a 5–15 s stall, and at 128K KV the `gemma4:12b` reload evicted the co-resident FIM runner. Pin `num_ctx` on every request (or bake it in the tag) whenever `OLLAMA_CONTEXT_LENGTH` is large. Evidence: `pair-cohab-20260828/attempt2-partner-reloaded-at-131072/`.

## 9. Pre-flight checklist for the IDEA-1090 campaign on timmy

1. Version: **decided 2026-08-28 — everything re-baselines on 0.33.1** (upgraded the same day). Rows measured on 0.31.1–0.32.13 (the 2026-08-14 matrix, slot probe, the first contention probe) are historical context only; do not mix them into a 0.33.1 table. Record `/api/version` per run regardless.
2. Confirm backend from the pod log (`ggml_vulkan: Using … RX 9070 XT`), not `ollama ps`; confirm `GGML_VK_VISIBLE_DEVICES=1`, `OLLAMA_LLM_LIBRARY=vulkan`, `CAP_PERFMON`.
3. Record live env from the deployment and the `server config` log line; note `CONTEXT_LENGTH=131072` vs the docs.
4. Isolation: `/api/ps` sampled over 30 s, no other consumer (harbor, matrix, an interactive session); remember the pinned FIM runner is an owner, and that loading anything else evicts it.
5. For every candidate model, a slot probe first: load with `num_predict:1`, grep `n_seq_max` / `new slot, n_ctx`; a 1-slot model cannot be measured for scaling.
6. Coherence gate per model at the row's sampling, best-of-N, with the think-tag-leak check; mandatory for nemotron (SSM_SCAN on Vulkan).
7. Thinking policy per row, explicit: `think:false` top-level on `/api/chat` (or `reasoning_effort:"none"` on `/v1/chat/completions`), verified by measuring the reasoning field; `num_predict` large enough that truncation is a model finding, not a harness one (16384 for agentic, ≥1500 minimum with thinking on).
8. Salted prompts; `prompt_eval_duration` for cache-hit detection; warmup excluded; `ollama stop` + cooldown between models; drift control model first and last.
9. Sampling pinned per model (Qwen precise-coding row for coders; gemma4's single row); `num_ctx` explicit per request, not inherited from a baked value.
10. Capture backend proof, slot lines and results **before** restoring the deployment; dated output dir; ConfigMap rebuilt after any script change; `kubectl cp` per config.
11. FIM contention leg (IDEA-1090 §sequence step 4): two runners (`qwen2.5-coder:fim` 3B + partner), agentic prefill-heavy load, target FIM TTFT p95 ≤ 1.62 s (IDEA-1071 baseline), FIM decode salted 2k-char prefix, 64 tokens, 8 reps.
12. Re-tests gated on version: gemma4 tool-call parser (replay the IDEA-1084 transcript), `n_seq_max` for qwen3.5/nano/ornith/lfm2.5, codegemma FIM cases (BUG-1036), and — if the run is on 0.33.1 — whether the metadata cache moves the 0.35 s idle FIM TTFT.
